# Changelog

All notable changes to Dash Forge are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
What a version number promises before 1.0 is described in [docs/VERSIONING.md](docs/VERSIONING.md).

## [Unreleased]

### Added

- **Move settings sync to a new key** ([#751](https://github.com/PastaPastaPasta/dash-forge/issues/751)). A site that tricks you into approving a wallet code gets your settings-sync key, and every wallet sign-in hands out the same one. **Settings → Storage → Move sync to a new key** and `dg storage sync move-key` make the next key from your recovery phrase, register it, disable the old one, and encrypt your synced settings and repository shares again under it; nothing of yours is deleted. Other devices add it once with **Add the new key** or `dg storage sync add-key`. After a move, wallet sign-ins no longer carry the sync key, and devices still holding the old one (released `dg` included) stop syncing until they add the new one ([guide](docs/guides/rotate-storage-credentials.md#if-a-site-may-have-your-settings-sync-key)).

- **Settings that follow your identity, on mainnet.** forge-user is registered on mainnet (`hxrzsQRUwprcekNur1N9ygc1zLX8jAuBaRTvnq3HmgK`, 2026-11-26, in contract group `H5gXhGVabbSdDdZMesVXevfbvNU8CgSCcHdhx6ekL2eJ`), so on mainnet as on testnet a wallet sign-in keeps your storage profiles (and in the web app your preferences) encrypted on Platform, and an owner can share a repository's storage with its maintainers. forge.dashhq.org has it from this change; `dg` from the first release after v0.3.1, which compiles the record in ([#750](https://github.com/PastaPastaPasta/dash-forge/pull/750)).
- **`dg auth login --wallet --any-identity`.** A wallet renewal's code now says which identity it renews ("This code renews alice.dash …"), because only that identity's answer is read. `--any-identity` lets any identity in the wallet answer instead ([#764](https://github.com/PastaPastaPasta/dash-forge/pull/764)).

### Fixed

- **A wallet renewal no longer asks about a master key it does not touch.** After a `--full-key` sign-in on a computer with a keychain, every wallet renewal asked about the master-key file and refused under `--yes`, though the wallet's key goes to the keychain. dg now asks only about what the store overwrites, says where the master key stays (`masterKeyKeptAt` in `--json`), and, when the keychain refuses the key, never falls back over a key file holding a master key or one it cannot open ([#764](https://github.com/PastaPastaPasta/dash-forge/pull/764)).

## [0.3.1] - 2026-11-26

`dg` and `git-remote-dash` work on testnet again. The [release notes](docs/releases/v0.3.1.md) say what broke, what changed and why mainnet is unaffected.

### Fixed

- **`dg` and `git-remote-dash` work on testnet again.** Testnet moved to Platform protocol 15 at 2026-11-25 19:41:30Z (epoch 20634, block 740732), before v0.3.0 was published. v0.3.0 is built on the Platform SDK 5.0.0-rc.8, which speaks only protocols 13 and 14, and much of it fails on testnet: resolving a DPNS name stops with `UnexpectedVariant … DataContractInSerializationFormat … found: 2`, clones and fetches stop with a proof error, and writes are refused. Reads by identity id still work. v0.3.1 is built on 5.1.0, which speaks protocols 14 and 15 and learns which one a network runs from its first proof-verified answer ([#756](https://github.com/PastaPastaPasta/dash-forge/pull/756), [#758](https://github.com/PastaPastaPasta/dash-forge/pull/758)). The web app at testnet-forge.dashhq.org, built from the same code, reads testnet again.
- **A document write the 5.1 SDK reports as unconfirmed is settled, not failed.** From 5.1 the SDK answers "state transition outcome is unconfirmed" when a send may have reached a node but it can't prove the result. `dg` and `git-remote-dash` treated every such answer as a failed write, and the web app did when the error it wrapped read as a refusal, although the write had often already been sent, so a rerun could sign a second copy. Now `dg` and `git-remote-dash` wait for the result, check whether the write landed and, if not, send the same bytes again; the web app checks whether the document landed and otherwise says the write is unconfirmed. Neither signs a replacement. Identity registration and key changes are not covered yet ([#759](https://github.com/PastaPastaPasta/dash-forge/pull/759)).

### Changed

- **Platform SDK 5.0.0-rc.8 → 5.1.0** in the Rust crates and the web app ([#756](https://github.com/PastaPastaPasta/dash-forge/pull/756), [#758](https://github.com/PastaPastaPasta/dash-forge/pull/758)). On mainnet, which runs protocol 14, what the tools write is unchanged: the protocol 14 serialization tables and document ids are the same in both SDKs.
- **Document history (an issue's, pull request's or comment's earlier revisions) pages by revision.** On protocol 15 each page continues after the last revision read; on protocol 14 it starts at the last revision's time and skips revisions already read ([#756](https://github.com/PastaPastaPasta/dash-forge/pull/756)).
- **Organization (testnet) BLS signing uses a pure-Rust library** (`blstrs_plus` 0.10) in place of blst's assembly, because the new SDK needs a newer blst than the old library allowed ([#756](https://github.com/PastaPastaPasta/dash-forge/pull/756)).

## [0.3.0] - 2026-11-26

The first release that knows Forge's mainnet contracts. The [release notes](docs/releases/v0.3.0.md) say what is new for mainnet users, what stays testnet only, and how to upgrade.

### Added

- **Forge on mainnet.** The four contracts (forge-core, forge-collab, forge-community and forge-meta) were registered on mainnet (chain id `evo1`, protocol 14) on 2026-11-24, in contract group `H5gXhGVabbSdDdZMesVXevfbvNU8CgSCcHdhx6ekL2eJ` ([#700](https://github.com/PastaPastaPasta/dash-forge/pull/700)). forge.dashhq.org now serves mainnet, and the testnet web app moved to testnet-forge.dashhq.org ([#678](https://github.com/PastaPastaPasta/dash-forge/pull/678)). v0.3.0 is the first release whose `dg` and `git-remote-dash` know mainnet; `dg auth login --network mainnet` makes it the default. v0.2.0 is testnet only.
- **Settings that follow your identity (testnet).** A new contract, forge-user, is registered on testnet. Wallet sign-in there adds an encryption key the wallet derives from its recovery phrase, and `dg` and the web app keep your storage profiles (and the web app your preferences) encrypted on Platform, so another computer or browser signed in with the same wallet sees them ([#729](https://github.com/PastaPastaPasta/dash-forge/pull/729)). Sync only adds what a device is missing; it never deletes or rewrites local settings. forge-user is not registered on mainnet, so there settings stay on each device; mainnet gets this in v0.4.0, once forge-user is registered there.
- **Storage for a repository's maintainers (testnet).** An owner can share storage set for one repository with its maintainers: `dg storage share <owner>/<repo> <profile>[,…] [--copies N]` (`--stop` ends it), or **Use separate storage for this repo to share it with maintainers** in the repo's Settings → Storage. Maintainers who signed in with a wallet store their pushes (when their git config sets no `dash.storage`), web merges and web release assets there and pay their own Platform fees; removing one moves the share to a new key. Only storage set for that repository is shared, never the owner's default storage ([#729](https://github.com/PastaPastaPasta/dash-forge/pull/729), [#740](https://github.com/PastaPastaPasta/dash-forge/pull/740)). A testnet share that an earlier build made from the default storage stops at the owner's next push, a maintainer change (`dg collab add … --role maintainer`, `dg collab remove`), `dg storage share` or visit to the repo's settings, and the owner is told once; nothing local is deleted ([rotate what maintainers saw](docs/guides/rotate-storage-credentials.md)).
- **Organizations (testnet).** A repository owner can be an N-of-M multisig identity made in multisig.dashhq.org: owner actions become requests its members sign (`dg org`, and the web app's organization pages). Off on mainnet ([#723](https://github.com/PastaPastaPasta/dash-forge/pull/723), [#724](https://github.com/PastaPastaPasta/dash-forge/pull/724); [Organizations](docs/guides/organizations.md)).
- **Run your own storage backend with one command.** `backend.sh` sets up, with Docker, an IPFS node whose API needs a token, behind Caddy, on a Linux server, PC or NAS, optionally with a public https name ([#719](https://github.com/PastaPastaPasta/dash-forge/pull/719); [Run your own backend](docs/guides/self-host-backend.md)).
- **The web app reads IPFS packs peer to peer** over libp2p in the browser, with HTTP gateways as the fallback ([#717](https://github.com/PastaPastaPasta/dash-forge/pull/717)).
- **A build for dash.site.** `pnpm build:dash-site` in `forge-web/` builds a copy of the web app for a dash.site static site: the docs pages redirect to the docs of another copy (`FORGE_DOCS_URL`), the Platform SDK's wasm loads from npm and is hash-checked, and the wallet sign-in names the dash.site address ([#726](https://github.com/PastaPastaPasta/dash-forge/pull/726), [#728](https://github.com/PastaPastaPasta/dash-forge/pull/728); [BUILDING.md](docs/BUILDING.md#the-dashsite-build)).
- **`dg auth status` and Settings say where the signing key came from**: a wallet, a recovery phrase or identity file, an exported `dfk1` key (`DASH_FORGE_KEY`), or an older keychain entry ([#666](https://github.com/PastaPastaPasta/dash-forge/pull/666)).
- **Pin a repository to your own storage, and fork onto it.** `dg repo pin <owner>/<name>` (and **Pin** on the repo page) copies every pack to your IPFS node or public bucket and records a pack mirror for each, so a clone still works when the repository's own storage is gone; `--follow` with `dg repo pin --all` keeps it current, and `dg repo unpin` removes the records. `dg repo fork` and `dg repo sync` now copy the parent's packs to your storage (the first readable profile in your storage policy, or `--storage`) and list your copy first; `--no-copy` keeps the old by-reference fork. The web app's repo page has **Fork** and **Pin** onto your own storage too ([#718](https://github.com/PastaPastaPasta/dash-forge/pull/718), [#720](https://github.com/PastaPastaPasta/dash-forge/pull/720)). See [Pin or fork a repository](docs/guides/pin-and-fork.md).
- **`dg auth export --new-key --scope core`** registers a limited key bound to the forge-core contract alone, with the usual budget and expiry: the narrowest key for a CI job that mirrors code and releases (`sync: code,releases`). It can write repositories and their settings and collaborators, refs, packs and releases; not issues, pull requests or stars, and on mainnet and testnet not labels or private repositories. It is not a code-only key: a leaked one can still add maintainers or writers, change protected branches and settings, and create or delete repositories. The default `--scope group` is unchanged, `--strict-group` is refused with `--scope core`, and `--json` reports `scope` with the `group` or `boundContract` the key is bound to. `dg auth keys list` and the web app's Devices & keys show such a key as a Forge limited key, bound to "forge-core only". See [The CI secret](docs/guides/mirror-a-github-repo.md#the-ci-secret) ([#713](https://github.com/PastaPastaPasta/dash-forge/pull/713)).
- **The mainnet and testnet web apps link to each other.** With the new Pages variables `PAGES_MAINNET_SITE_URL` and `PAGES_TESTNET_SITE_URL` set, the Networks page has an "Open Forge on Mainnet" or "Open Forge on Testnet" link for the other live network, a testnet build shows a dismissible "Forge is live on mainnet" banner once mainnet has Forge's contracts, and the mainnet footer links the testnet site. Rebuilding a hosted build to verify it now needs both values (see [Verify the app](docs/guides/verify-the-app.md)). See [Linking the mainnet and testnet sites](docs/hosting.md#linking-the-mainnet-and-testnet-sites) ([#685](https://github.com/PastaPastaPasta/dash-forge/pull/685)).
- **`dg auth login --wallet`**: sign in from the terminal with the DashPay wallet on your phone (App Connect). `dg` prints a QR code and a `dashpay://connect` link, the wallet adds a limited key (proposed: 0.25 DASH for 180 days; the wallet may change it), and `dg` reads the answer from Platform, shows the identity to confirm and stores the key like any limited key. `dg auth status` shows such a key as "from your wallet (App Connect)". Testnet needs DashPay's testnet build. See [Signing in from the terminal with DashPay](docs/guides/identity-and-keys.md#signing-in-from-the-terminal-with-dashpay) ([#663](https://github.com/PastaPastaPasta/dash-forge/pull/663), [#712](https://github.com/PastaPastaPasta/dash-forge/pull/712)).

### Changed

- **Repo Settings shows one section at a time**, picked from a section nav, so a link such as `#storage` opens that section ([#725](https://github.com/PastaPastaPasta/dash-forge/pull/725)).
- **Quieter repo, browse, settings and start screens.** Each screen leads with its main action; verification details, storage badges, clone options and cost notes moved into collapsed sections ([#708](https://github.com/PastaPastaPasta/dash-forge/pull/708), [#709](https://github.com/PastaPastaPasta/dash-forge/pull/709)). A commit with no checks says so in one line ([#671](https://github.com/PastaPastaPasta/dash-forge/pull/671)), and a merged or closed pull request no longer shows the live approvals and checks cards ([#669](https://github.com/PastaPastaPasta/dash-forge/pull/669)).
- **A Platform write says what it is doing** while it waits, and a slow one ends calmly instead of in a red error ([#649](https://github.com/PastaPastaPasta/dash-forge/pull/649)). An empty repository walks its owner through the first push in three steps ([#650](https://github.com/PastaPastaPasta/dash-forge/pull/650)).
- **ipfs.dashhq.org is first among the default IPFS gateways** (after a repository's own gateway), with fewer and larger range requests; public gateways stay the fallback ([#702](https://github.com/PastaPastaPasta/dash-forge/pull/702)).
- **`dg ipfs up` and `dg ipfs connect` no longer open a browser.** They print the link, the code and its expiry; `--open` opens the link too ([#727](https://github.com/PastaPastaPasta/dash-forge/pull/727), [#695](https://github.com/PastaPastaPasta/dash-forge/pull/695)). The node also allows testnet-forge.dashhq.org.
- **`dg`'s web links follow the network**: testnet links and the CORS document name testnet-forge.dashhq.org, and the out-of-credits hint names the right top-up page for the network ([#691](https://github.com/PastaPastaPasta/dash-forge/pull/691)).
- **On testnet the sign-in sheet leads with the wallet**, now that DashPay for Android's testnet build answers App Connect v2 ([#655](https://github.com/PastaPastaPasta/dash-forge/pull/655)).
- **The web app's wallet sign-in is simpler.** The QR step shows the code, "Open DashPay → Connections and scan", the countdown, **Copy link** and **Open in wallet**, and one line saying to scan only codes shown on this site. The spending limit, expiry, phishing detail and supported wallet versions are under **Details**, and the link is no longer printed under the code. After the wallet answers, the sheet says who signed in, with **That's me, continue** and **Not me, start over**. The warning about a username registered in the last day is gone.
- **Signing in no longer requires a passkey or passphrase.** After sign-in the next step is **Add a passkey**, with **Skip for now** and a **Use a password instead** option. A skipped key stays in this browser, sealed under a key the browser keeps, and reopens on page load without a prompt unless "Stay signed in" is off. It is only the browser's spend-capped, expiring key; a key with no spending limit still needs a passkey or passphrase.
- **On mainnet, signing in or creating an identity with a recovery phrase or identity file is under Advanced** in the sign-in sheet.
- **On mainnet, no normal flow in the web app asks for your recovery phrase or identity file.** The top-up sheet says to buy credits in DashPay and check again, renews a wallet's key in the wallet, and otherwise offers signing in again with the wallet. Settings → This browser's key keeps Renew in your wallet, Lock and Sign out in view. Devices & keys points to DashPay → Connections for wallet sign-ins. Adding a username points to DashPay. Each master-key action (top up the key, renew or revoke with the identity file, disable keys, register a username here, add an encryption key, top up from this browser) is still there behind one collapsed "Advanced" disclosure. Testnet and devnets show them in place.
- **The web app's sign-in sheet shows two choices: Use my Dash wallet (recommended) and Sign in with a passkey.** Every other way in sits under one collapsed **Other ways to sign in**: getting DashPay, the recovery phrase or identity file, dg, creating an identity, the browser key's limits, Advanced and the glossary. Where no released wallet can finish sign-in (a devnet, or a chain without App Connect v2), creating an identity shows beside the passkey instead.
- **The web app's wallet sign-in QR code and "Open in DashPay" link use `dashpay://connect`**, the App Connect DIP's link (`dashpay://connect?v=2&n=…&r=…`), on every network. It replaces `dash-key:`, which wallets refuse on mainnet. The request inside it is unchanged, and it still works with DashPay for Android 11.9.2 or later and Dash Wallet for iOS 9.1.4 or later.
- **On mainnet, the web app's sign-in sheet sends newcomers to DashPay first** (visible once Forge is deployed there). Where the wallet can sign you in (App Connect v2), the "New to Dash?" tile becomes **Get DashPay, create your identity there, then sign in**: it names DashPay for Android and Dash Wallet for iOS, links the DashPay Wallet releases, and opens the wallet sign-in. Creating an identity in the page is still there, under **Other ways to sign in**. Testnet and devnets are unchanged: creating an identity in the page stays the newcomer's first option.
- **On testnet, the web app renews every browser key in your DashPay wallet first** (Settings, the low-funds banner, the top-up sheet), with the identity file or recovery phrase beside it. For a key the wallet didn't grant to this browser, the wallet adds a new key and the old one stays live, held here never to sign so a renewal with the identity file or recovery phrase, or a revoke, disables it (as does a first wallet sign-in while that vault is unlocked). A wallet's older unlimited key is still replaced with the master key. Revoking a key the wallet granted leads with disconnecting Dash Forge in the wallet when no such held key is left; the recovery-phrase revoke stays below it. Mainnet routing is unchanged; its help text for a key a passkey restored now says the wallet leaves the old key live, as it always did.
- **A bare `dg auth login` signs in with your DashPay wallet** (as `--wallet` does): it prints the QR code and the `dashpay://connect` link. `dg auth login <file>`, `--mnemonic`, `--full-key` and `--replace` sign in from the identity's master key as before. Without a terminal (stdin is not one, or `--json`) a bare `dg auth login` used to be a usage error (exit 2); it is now [E802](docs/errors.md#e802) (exit 8), and it shows and stores nothing: scripts pass an identity file, or `--wallet --yes`, or set a dfk1 key in `DASH_FORGE_KEY`. The no-key messages of `dg`, `git-remote-dash` and the Action, the docs and the web app's empty-repository steps name `dg auth login` first.

### Removed

- **The web app no longer offers the older wallet code (v1 DashConnect).** Gone: "Show the older code", its per-contract approvals and the guided "Step 2 of 3" grants that followed a sign-in. Wallet sign-in is App Connect v2 only. Where v2 can't be offered (devnets, or when Platform can't be asked), the sheet leads with the recovery phrase, the identity file or creating an identity, and Advanced keeps the pasted key. Nothing is deleted from your browser: a key the older code left still unlocks and signs where it reaches, and its encryption keys stay in the vault. When it lacks a spending limit or doesn't cover a write, **Replace with a limited key** now asks your wallet first, with the identity file or recovery phrase beside it; after a wallet replacement the old keys are held never to sign, so a renewal with the identity file or a revoke still disables them. A repo wrapped to an encryption key from another approval of the older code now says no import can bring it back and points to Repair. The sign-in sheet's order is pinned by tests for mainnet, testnet and devnet.

### Fixed

- **`git-remote-dash --help` and `-h` print the usage** and exit 0. They used to fail with E101 ("unknown admin command") and E203 ([#749](https://github.com/PastaPastaPasta/dash-forge/pull/749)).
- **`dg storage share` says how to rotate a shared profile's credentials:** when only its secret changed, E502 now says to re-run `dg storage add <name>` with the new secret (testnet; [#742](https://github.com/PastaPastaPasta/dash-forge/pull/742)).
- **Explore's Trending no longer fails with "this network runs protocol version 13"** on a slow first visit: the web app seeds the Platform SDK at the deployment's protocol version before it connects ([#744](https://github.com/PastaPastaPasta/dash-forge/pull/744)).
- **Explore hides rankings with nothing to list, and on phones a commit's message gets the whole first line and the repo header's actions stay on one row** ([#745](https://github.com/PastaPastaPasta/dash-forge/pull/745), [#746](https://github.com/PastaPastaPasta/dash-forge/pull/746), [#747](https://github.com/PastaPastaPasta/dash-forge/pull/747)).
- **A key `dg` replaces is kept.** Signing in again (with the wallet, an identity file or a recovery phrase) or renewing a key used to overwrite the key `dg` stored for that identity, a master key included, with no copy. `dg` now copies the old key first: the key file to `<network>-<id>.key.bak-<UTC time>` beside it (0600), a keychain entry to one named `….bak-<UTC time>`, never over an earlier copy, and says where it went (`previousKeyKeptAt` in `--json`). A key file it can't read is not replaced ([#741](https://github.com/PastaPastaPasta/dash-forge/pull/741)).
- **Dash Wallet for iOS no longer refuses the web app's sign-in code as "dated ahead of the network's time".** ([#705](https://github.com/PastaPastaPasta/dash-forge/pull/705)) The request's creation time came from the browser's clock, and the wallet compares it with Platform's latest block time, which can be minutes behind on mainnet. It is now the browser's clock held within 90 seconds of the chain time Forge read.
- **Connecting a node from the web app works on the first try.** A late **Allow** on the browser's local-network prompt no longer ends in "The node blocked this site" ([#727](https://github.com/PastaPastaPasta/dash-forge/pull/727)).
- **`dg` warns when `DASH_FORGE_NETWORK` names a different network** than the one it uses, since `git push` would follow the variable ([#698](https://github.com/PastaPastaPasta/dash-forge/pull/698)).
- **`dg repo clone` and publishing say `git-remote-dash` is missing** before running git, instead of git's raw error and E101 ([#696](https://github.com/PastaPastaPasta/dash-forge/pull/696)).
- **The Action's runner-key renewal warning points at a page that exists** ([#684](https://github.com/PastaPastaPasta/dash-forge/pull/684)).
- **Offline on testnet or mainnet, errors no longer blame a devnet name** ([#694](https://github.com/PastaPastaPasta/dash-forge/pull/694)).
- **In the web app, commits GitHub signed (such as imported merges) read "Signed by GitHub" instead of Unverified**, and a signature by a key on nobody's profile reads "Signed" (SSH) or "Unknown key" (OpenPGP) ([#701](https://github.com/PastaPastaPasta/dash-forge/pull/701)).
- In the web app: no **Follow** on a profile whose id is no identity ([#693](https://github.com/PastaPastaPasta/dash-forge/pull/693)); a private create with no encryption key in the browser no longer asks for an unlock that can't help ([#692](https://github.com/PastaPastaPasta/dash-forge/pull/692)); an out-of-range issue or PR number shows the "No issue addressed" page instead of a network error ([#686](https://github.com/PastaPastaPasta/dash-forge/pull/686)); a mistyped Identity ID on the recovery-phrase sign-in says what is wrong ([#687](https://github.com/PastaPastaPasta/dash-forge/pull/687)); a file under a missing directory says it isn't on this ref ([#668](https://github.com/PastaPastaPasta/dash-forge/pull/668)); a browser-only key unlocked in the same millisecond as a lock stays openable ([#722](https://github.com/PastaPastaPasta/dash-forge/pull/722)).
- **forge-notify accepts wallet-granted keys** (`ECDSA_HASH160`), so people signed in with a wallet can set up email and push notifications ([#659](https://github.com/PastaPastaPasta/dash-forge/pull/659)).
- **Renewing a key this browser registered itself in your wallet** no longer says to approve "in the wallet that gave this browser its key" (no wallet gave it). It says to approve in the wallet that holds this identity.
- **The web app loads on a slow link, and says so calmly when it can't.** Every quorum key request took about 6 s, but wasm-sdk aborts each one at about 5 s, so the page retried forever and never loaded. Quorum key requests now get 20 s of their own. A good answer is kept in the browser for a day (the keys are public), and is used when the quorum service is slow or down. Reconnects back off (5, 15, 30 and 60 s) and then stop with "It stopped retrying on its own. Check your connection, then choose Try again", instead of spinning. They retry once more when the tab comes back into view or the browser goes back online.
- **A wallet's key, or one a passkey restored, that was disabled on Platform (a wallet disconnect) now says so.** Unlocking it, a page load that resumes it, the next balance read, or a notification-service request signs out with "This key was disconnected in your wallet, so sign in again" (for a passkey-restored key: "disabled on Platform (disconnected in your wallet, or revoked from another device)"), flags the stored key, and offers **Forget this key and sign in again**. Before, it said "no longer usable … renew it" and offered a renewal that needs the recovery phrase. Platform writes already refused it: each checks the key on chain before signing. Notification-service requests didn't check it, and a service caching keys could accept them for up to a minute; they now check first.
- **`dg pr diff` of a merged pull request shows the changes it brought in** ([#670](https://github.com/PastaPastaPasta/dash-forge/issues/670)). It used to print nothing and exit 0: it diffed the base as it is now, which contains the head once the PR is merged. A merged PR is now compared from the base tip its merge built on (as the web's Files changed tab and `dg pr verify` do), against the head as it was merged, and says so on stderr. The base or head branch being deleted since does not matter: the commits come from the repository's packs. `--json` adds `comparedWith` (`base`, `tipBeforeMerge` or `baseNow`).
- **`dg repo view` says in plain words when it couldn't check for a security policy**, and what to do next. Without `git-remote-dash` installed it used to print git's raw error ("git: 'remote-dash' is not a git command … fatal: remote helper 'dash' aborted session"). It now prints "Security policy: not checked (git-remote-dash isn't installed …)" under the repository, with a `next step:` line: install the helper, then `dg repo clone`. `--json` adds `securityPolicyNote` (the plain words) and `securityPolicyError` (the raw cause).
- **`dg pr diff` works outside a clone**, as `gh pr diff` does: it fetches into a scratch repository and removes it afterwards. It used to fail with E101 ("report it") because git found no repository. Inside a clone it still fetches there, so the objects stay for next time. `dg pr checkout` outside a repository now says it needs one ([E206](docs/errors.md#e206)) instead of E101.

### Security

- **forge-notify refuses requests signed by an expired identity key** ([#662](https://github.com/PastaPastaPasta/dash-forge/pull/662)).

## [0.2.0] - 2026-11-22

Dash Forge moves to **testnet**: its four contracts are registered there, and testnet is now the supported network for `dg`, `git-remote-dash`, the web app and the Actions. Devnet sakura, which v0.1.0 targeted, is down, and nothing on it was carried over. See the [release notes](docs/releases/v0.2.0.md) for networks, upgrading and known limitations.

Members-only content in public repositories, Environments and the secret scan. People using older Forge builds see fewer things until they update: they leave members-only items out, and they don't count a members-only review's approval, so they may refuse a merge an up-to-date build allows. **Update to see and count members-only reviews.** [Who can read what](docs/security/audiences.md) explains the audiences, what stays public and what can still leak.

### Added

- **Forge on testnet.** The production four-contract set (forge-core, forge-collab, forge-community and forge-meta) was registered on testnet (`dash-testnet-51`, Platform 5.0.0-rc.8, protocol 14) on 2026-10-26, in contract group `EXgzBMpwC7RMjSU4WQghLAnfboswsssMGiXRtiV1hmBC`, from the same JSON that will be registered on mainnet. The record is `forge-contracts/deployments/testnet.json`, with its evidence in `forge-contracts/evidence/testnet/`. Testnet is every tool's default network, so `dg auth new` needs no flags.
- **Members-only content in public repositories.** A maintainer turns it on once with `dg repo members enable` (it shows the cost first: about 0.004 DASH for 5 members), and `dg repo members status` shows who has the key. Members can then post issues, comments and reviews only members can read: maintainers, writers, triage members and readers, including members added later. Removed members keep what they could already read. CI runners are not members. Everyone can still see that something was posted, by whom, when and how large, and a review's verdict.
- **Members-only discussion from `dg`** in public repositories with members-only content turned on: `--members` on `dg issue create`, `dg issue comment`, `dg pr comment` and `dg pr review`. Members read it in `dg issue view/list` and `dg pr view/list`; everyone else sees "#3 · members-only issue by @alice · open" and "3 members-only comments hidden". Every item in `--json` carries `"audience"` and `"readable"`. A members-only text longer than its field is stored encrypted (by maintainers and writers), and a members-only pending review is kept encrypted on disk.
- **Readers on public repositories.** `dg collab add --role reader` works on public repositories: a reader follows the members-only discussion without pushing or merging.
- **Membership changes follow the members key.** On a repository with members-only content, `dg collab add` shares the key with the new member and `dg collab remove` changes it, as on a private repository. `dg repo keys status`, `repair` and `rotate` work there too. A member added by an older build sees E311 until a maintainer's repair shares the key.
- **A members-only review's approval counts for everyone**, member or not, so everyone sees the same merge button.
- **The web app** reads members-only issues, comments and reviews for members after one unlock per tab, keeps a reply in a members-only conversation members-only, offers the reader role on public repositories, and shares or changes the key when members are added or removed.
- **Members-only content in the web app.** A maintainer turns it on with **Turn on members-only content**, which shows the cost first. Every composer has an audience chip (Public or Members). Everyone else sees members-only rows, placeholders and a "#N · members-only" page, never the text. Members can check the public's view with **View as public**. The web asks before a public post that quotes members-only text, and keeps no members-only draft on disk. A removed member still reads what was written while they were a member.
- **Settings → Environments** in the web app shows a repository's environments to the people who can read them, with values hidden until you show one; others see only how many there are. Changes are made with `dg env`.
- **Environments** (`dg env`): configuration and secrets kept outside git, encrypted for a repository's **Maintainers** (the default for `production`, `prod*`, `staging` and `release*`) or its **Members**, changed by maintainers only, injected with `dg env run` or written to a git-ignored file with `dg env export -o .env`. Two changes at once fail closed (E608) until a maintainer keeps one. `dg collab remove` lists the values the removed member could read. See [Environments](docs/guides/environments.md).
- **Secrets in a public push.** `git push` to a public repository checks every file it publishes for the first time. It refuses a new `.env` file, a PEM private key, an AWS key pair or a GitHub or GitLab token with a valid checksum (E807), and warns about `.envrc` files, random-looking values and keys in test folders. `-o allow-secret=<fingerprint>` or `.forge/secret-scan-allow` lets a checked finding through. See [Secrets in a push](docs/guides/quick-start.md#secrets-in-a-push).
- **Wallet sign-in keeps your encryption key.** The web app stores the encryption key the Dash Wallet registers in the browser's vault, every one of them across approvals, so private repositories and members-only content open after one unlock per tab. When the identity's key came from somewhere else, it says "Your encryption key is held elsewhere. Import it under Settings → Private repos."
- **Wallet sign-in with App Connect v2: one approval for all of Forge.** Where the network runs protocol 14 and Forge is deployed (testnet, since 2026-10-26), the wallet tile comes first and shows an App Connect v2 request: the wallet adds one key for this browser that works on every Forge contract, capped at 0.05 DASH of spending and expiring after 90 days (a wallet may offer other limits), so the extra approvals of the older exchange are not asked for. The phone link returns to a new `/connect/` page, and the sign-in checks the wallet again when the tab regains focus. A key a wallet granted is renewed in that wallet (**Renew in your wallet**, in the low-funds banner, the top-up sheet and Settings → This browser's key); the identity file or recovery phrase still works. If your wallet's build has no App Connect v2, **Show the older code** gives today's request. A v2 sign-in does not bring an encryption key: set up private and members-only content in Settings. We know of no released Dash Wallet that speaks App Connect v2 yet; the [wallet sign-in notes](docs/design/wallet-login.md#app-connect-v2-one-approval-for-all-of-forge) say what works today.
- **Passkeys for other devices (web app).** **Settings → Devices & keys → Passkeys for other devices** adds a passkey that holds this browser's key, encrypted to it, on Platform. On another device, **Sign in with a passkey** brings that sign-in over: the same key and budget, checked against your identity before it is used. A passkey moves a session, it doesn't recover an account: when the key expires or is disabled it stops working, and you renew with your identity file, recovery phrase or wallet (a session restored from a passkey offers both **Renew in your wallet** and **Renew with identity file**). Keys without a spending limit or an expiry stay on the device that holds them, because the encrypted copy is public on Platform for good. Your encryption key is included only if you tick it, with a warning that it can't be taken back. After signing in, the web app offers a passkey once (twice at most, never after **Not now**). Revoking or disabling a key offers to remove the passkeys that hold it. Adding one costs about 0.0005 DASH from the key's budget; signing in is free. It works at forge.dashhq.org only. The controls show only where forge-meta has the new `vaultEntry` type: on testnet since its forge-meta update to version 2 (2026-10-26). See [Passkeys: the threat model](docs/security/passkey-vault.md) and [identity and keys](docs/guides/identity-and-keys.md#passkeys-for-other-devices).
- **Boards in the web app.** A repository's **Boards** tab lists its boards; each opens as a kanban, a table or a roadmap, with saved views, fields (priority, estimate, iteration), quick add and drag-and-drop. Every issue and pull request page has a **Boards** sidebar section. A new board starts from a template (Kanban, Sprint, Triage or Empty). See the [Boards guide](docs/guides/boards.md).
- **`dg board`.** List, view (`--view`, `--json` with the fold), create (the web's templates or `--columns`), move (`--top`, `--before`, `--after`), set fields, add (or open a new issue with `--title`), archive, remove, move to the next iteration, close and delete boards from the command line, private repositories' sealed boards and cards included ([Boards guide](docs/guides/boards.md)). forge-core reads and writes boards and cards as the web does, and runs the `sealed_board` vectors.
- **Board contract types.** forge-meta gains `board` and `card` (UPDATE-3, [boards design](docs/design/boards.md) §3), written only by the home repository's members; testnet got them on 2026-10-27 by an in-place update of forge-meta to version 3 ([evidence](forge-contracts/evidence/testnet/README.md#forge-meta-update-to-version-3-boards-2026-10-27)).

### Changed

- **Testnet is the supported network.** forge.dashhq.org, the IPFS release build, the guides, the Mirror Action, the check action and the GitLab CI template default to testnet, and their faucet links go to the Dash testnet faucet and faucet.thepasta.org. The Mirror Action's and the check action's `devnet-name` input now defaults to empty. A workflow that set `network: devnet` and `devnet-name: sakura` must drop both. [Dash Forge moved to testnet](docs/guides/devnet-move.md) says how to re-push from a clone.
- `dg repo view` counts git packs only: `packCount` and `packBytes` (and the `packs:` line) no longer include browse indexes, history indexes, release-asset lists or long bodies. `dg storage status` still lists every artifact.
- Notifications and `forge-relay` webhooks never carry members-only text: they say that something happened, by whom and where. An encrypted comment or review from someone who is not a member is not shown and notifies nobody.
- **The web app asks only the Dash network's evonodes** for an identity deposit: the Insight fallback and the **Fallback block explorer** setting are gone. It watches the deposit on two nodes at once, and moves a feed that fails or goes silent to another node.
- **forge.dashhq.org carries its Cloudflare Web Analytics beacon in the build** ([#618](https://github.com/PastaPastaPasta/dash-forge/pull/618)), so Cloudflare no longer has to inject it. The beacon is pinned by URL and SRI hash, the page CSP allows only that URL, and only a build given `NEXT_PUBLIC_CF_BEACON_TOKEN` has it: the IPFS build never does, and a self-hosted build only if you set the token. `dg verify-app` matches once Cloudflare's zone is switched to the JS-snippet setup, which stops its own injection. **Privacy:** forge.dashhq.org counts visits with Cloudflare Web Analytics (page path and referrer, browser, country, load times). Cloudflare says it sets no cookies, uses no local storage and does not fingerprint visitors. The beacon runs with the page's privileges, and the site's `Referrer-Policy` is now `strict-origin` instead of `no-referrer`, so linked sites see `https://forge.dashhq.org/`. Blocking `static.cloudflareinsights.com` changes nothing in the app. [docs/hosting.md](docs/hosting.md) §6 and the [FAQ](docs/FAQ.md) have the details.

### Fixed

- **`git push` asks before the whole push, not one pack at a time.** The cost guard weighs every pack (public and members-only), every index and every ref update together, once, before anything is paid. A push of tags or branches at commits already stored (`git push --tags`), and a push that only deletes, used to write its ref updates without a question: 300 tags is about 0.28 DASH.
- **`dg pr merge --yes` approves the price it shows, and no more.** The merge is built before the question and priced by a dry run of its push. The push is then capped at that price: a dearer push is refused (E801) before anything is paid. `dg pr revert --yes` and `--delete-branch` work the same way.
- **`dg pr merge --override-policy` fails (E106) when the merge landed but its policy-bypass record did not**, instead of printing "merged" and exiting 0. `--record-bypass` records the missing bypass.
- **`dg import` and `forge-import` without `--max-spend` stop at the estimate you confirmed** instead of running uncapped.
- **The Mirror Action's recommended workflow no longer runs on issue, comment and pull request events**, which anyone can trigger. Mirroring them is an opt-in that the README explains, with its risk. An identity file as `DASH_FORGE_KEY` (no key budget) is refused unless `allow-unlimited-key: 'true'`.
- **forge-runner retries a check's final report** with backoff. If the report still doesn't land, the runner keeps it and resends it on the next polls (up to 48), instead of marking the run done with the check left running. The jobs are not run again.
- **The web app prices an edit of a long issue, PR or comment with its long-body storage**, so the confirmation and its balance check show what the edit costs.
- **A push that merges every live head of a diverged branch settles it.** Before, a merge of both heads paid for its write, left the other head live and reported "lost concurrent race" on every later push until `--force`. If one of the settling updates fails, the push now says which head is still live instead of reporting nothing written.
- **A flood of reviews can no longer block a merge.** Approvals are counted from members' verdicts on the PR's head, read on their own index, instead of from the whole review list, which anyone could pad past the complete-read cap.
- **The web app runs only its own inline scripts in production.** Each exported page carries a second content policy that lists the SHA-256 of its inline scripts, so a script a host injects into the HTML (a CDN's analytics beacon, say) does not run beside the key vault.
- **A browser merge or Update branch checks the base before paying for the pack**, and stops with "nothing was written" when the branch moved or diverged, instead of uploading a pack nothing could use.
- **A partial clone's lazy blob fetch reads only the packs that hold the blobs** it needs, instead of downloading the whole repository again for each checkout, `git log -p` or blame.
- **Issue and PR lists say when the repository's label definitions were not read completely**, instead of presenting the first page as all of them.
- **A removed member's sealed author events on their own issues and PRs follow the late-content rule**, so they can no longer keep writing readable values under an old key.
- **Trending loads in a fresh tab on testnet.** A new connection learns the network's protocol version before the first page query. Before, the SDK started at protocol 13 and refused Trending's time-range read with "requires protocol version 14+" until you clicked Try again.
- **InstantSend proofs on testnet.** Creating or topping up an identity, in the web app or with `dg auth new`, waited on `getislocks` at `trpc.digitalcash.dev`, which no longer follows testnet, so every lock fell back to a slower chain-lock proof. The InstantSend lock now comes off DAPI `subscribeToTransactionsWithProofs` feeds on three evonodes, opened before the asset lock is broadcast, as in govhub and mainnet-bridge. `--islock-rpc` and `islock_rpc` still add an RPC of your choice, but none is set by default.
- **Every issue and pull request page said "This page couldn't read the boards"** ([#621](https://github.com/PastaPastaPasta/dash-forge/pull/621)). The sidebar's card query put an `in` clause where Drive refuses one, so testnet rejected it. The web app and `dg` now read the item's own repository exactly, and the owner's other public repositories with one bounded read.
- **`/<owner>/<repo>/boards` and `/boards/<key>` links open the Boards pages** instead of "Nothing here" ([#621](https://github.com/PastaPastaPasta/dash-forge/pull/621)).
- **An empty repository and the mirror wizard tell an identity made in the browser to run `dg auth login --mnemonic`**, not `dg auth login <identity file>`, which it doesn't have ([#621](https://github.com/PastaPastaPasta/dash-forge/pull/621)).
- **`dg import` with the GitHub CLI signed out fails with [E204](docs/errors.md#e204)** and says to run `gh auth login` or set `GH_TOKEN`, instead of E101 "report it as a bug" ([#621](https://github.com/PastaPastaPasta/dash-forge/pull/621)).
- **The out-of-credits hint (E401) points to the web app's Top up credits sheet.** It said the testnet faucet "funds an identity", but the faucet pays Core addresses only ([#621](https://github.com/PastaPastaPasta/dash-forge/pull/621)). The deposit step's amounts read as one sentence.
- **`dg repo clone` and `dg init` record `dash.network` in a testnet clone** ([#619](https://github.com/PastaPastaPasta/dash-forge/pull/619)). Testnet is the built-in default, so a testnet clone used to count as pinned with nothing recorded, and a later `dg auth` default (a devnet or mainnet) would move its plain `git push` to that network. A clone now also records the DAPI addresses set in dg's config. Clones made by earlier builds: run `git config dash.network testnet` in each.
- **`dg pr merge` no longer reports `"merged": false` for a merge that landed** ([#619](https://github.com/PastaPastaPasta/dash-forge/pull/619)). When the PR read straight after a confirmed merge came from a lagging node, dg said the merge was only recorded; it now reads again for up to about 15 seconds first.
- **The Star button's accessible name is its visible text** (`Star 3`, `Starred 3`); the price moved to its description ([#620](https://github.com/PastaPastaPasta/dash-forge/pull/620)).
- **`dg verify-app` passes on forge.dashhq.org while Cloudflare injects its analytics beacon.** Cloudflare's Web Analytics automatic setup stays on there and adds a second beacon tag before `</body>` of every page, so every page differed (E504) and the nightly check failed. `dg verify-app` now removes exactly that tag, in Cloudflare's own form and only beside the build's beacon for the same site token, before hashing a page, and counts those pages (`cfBeaconRemoved` in `--json`). Any other difference still fails. The second tag counts no visit twice: the browser runs the beacon once, and the page CSP refuses any other beacon version ([docs/hosting.md](docs/hosting.md) §6).

## [0.1.0] - 2026-10-04

The first release. It targets devnet sakura (Dash Platform v5.0.0-beta.1, protocol 14) only;
testnet and mainnet are not supported yet. See the [release notes](docs/releases/v0.1.0.md)
for networks, installation, verification and known limitations.

### Added

- **Git hosting over `dash://`**
  - `git-remote-dash`, a git remote helper: `git clone dash://<owner>/<name>`, `git push`, branches, tags, force-pushes and partial clones (`--filter=blob:none`); jj works too.
  - Refs and pack manifests are signed documents on Dash Platform; every push prints its cost before it pays, and a cost guard can make it ask.
  - DPNS usernames in place of identity ids (`dash://alice/project`), resolved with proof-checked reads.
- **The `dg` command-line interface**, shaped like `gh`
  - Repositories, forks and fork sync, stars, watches, issues, pull requests, reviews, merges, releases, labels, milestones, members, webhooks, check runs and public profiles.
  - `dg init` publishes an existing git repository in one step; `dg doctor` checks the setup.
  - Search within a repository (`dg search`), raw proof-checked queries (`dg api query`), and spend estimates and audits (`dg cost`).
  - Error codes with documented fixes ([docs/errors.md](docs/errors.md)), `--json` output, and shell completions for bash, zsh, fish and PowerShell.
- **Bring-your-own storage**
  - Packs go to an S3-compatible bucket (Cloudflare R2, Backblaze B2, AWS S3, Storj, MinIO, Garage, RustFS), an IPFS node or pinning service, or Platform itself, with N-of-M replication.
  - Set up with `dg storage add` or the web app's storage wizard; readers accept only bytes that match the SHA-256 recorded on chain and fall back to the next copy.
  - `dg reseed --from-local` restores a lost copy from any clone; `dg repack` consolidates packs.
- **Identities and limited keys**
  - `dg auth new` creates an identity from 12 recovery words and a deposit; `dg auth login` imports one from an identity file or the words.
  - Day-to-day signing uses limited keys: a budget, an expiry, and usable only on Forge's contracts, enforced by Platform. CLI keys live in the OS keychain (or a passphrase-sealed file); the master key is not stored by default.
  - Key management (`dg auth keys`), DPNS username registration, and `dfk1:` runner keys for CI.
- **Collaboration**
  - Members with reader, triage, writer and maintainer roles, enforced at consensus; adding a member needs their consent first.
  - Issues with labels, milestones, assignees, locking, pinning and maintainer hiding (nothing is deleted); comments editable and deletable by their author.
  - Pull requests from a branch or a fork, with inline review comments, suggestions, pending reviews, draft state, base retargeting and code owners (`CODEOWNERS`) asked for review.
  - Real merges from `dg pr merge`: fast-forward, merge commit, squash or rebase; protected branches enforced by Platform, and a branch policy (required approvals, allowed merge methods) with a recorded maintainer bypass.
  - Releases with hash-checked assets, yanking and unpublishing; maintainers and writers can post descriptions, comments and release notes over 5 KiB, stored as repository artifacts.
  - Archived repositories, repository topics, follows, and Verified badges for commits signed with a key published on the signer's profile (`dg verify-commit`).
- **Private repositories**
  - `dg repo create --private` (or the web app): code, branch names, issues, pull requests, comments, reviews and releases are encrypted to members' encryption keys; removing a member rotates the key.
  - What stays visible (the repository's existence, name, members, sizes, timing, commit ids, label definitions, check runs) is listed in the [collaborating guide](docs/guides/collaborating.md#private-repositories).
- **The web app** at [forge.dashhq.org](https://forge.dashhq.org), a static site with no backend
  - Browse code, commits, branches, tags, blame, history and diffs; download a branch as a zip; search a repository's code in the browser.
  - File and triage issues; open, review and merge pull requests; fork and sync repositories; create and delete branches; publish releases; manage members, settings, storage, labels and milestones; issue and PR templates.
  - Explore, trending, a local notifications inbox, public profiles, and a spend ledger. Every write shows its price before you sign.
  - A Verification card on every repository page that reports what was proven, including a cross-check of the quorum keys against a second source.
  - Sign in by creating an identity in the browser, importing one, or scanning a QR code with Dash Wallet (no released wallet answers it yet; see [Known limitations](docs/releases/v0.1.0.md#known-limitations)). Keys are kept in an encrypted vault unlocked by a passkey or passphrase.
- **Mirroring**
  - `forge-import` (and `dg import`) copies a GitHub repository's code, issues, pull requests, reviews, releases and labels, under a spending cap; GitLab projects are supported as a source too.
  - The Mirror Action keeps a copy in sync from GitHub Actions, idempotently and under a per-run cost cap; the web app's `/mirror` wizard sets it up.
  - A GitLab CI template ([integrations/gitlab](integrations/gitlab/README.md)) does the same from GitLab.
- **CI**
  - Check runs on commits and pull requests, reported by `dg ci report` under a runner key that can sign nothing else, with logs and artifacts checked by hash; re-runs from the web and `dg`.
  - `forge-runner`, a self-hosted runner that runs a repository's `.forge/workflows` (GitHub Actions syntax) with nektos/act in Docker.
  - The check action reports GitHub Actions jobs as Forge check runs.
  - `forge-relay`, a relay you run yourself, turns on-chain activity into GitHub-shaped webhooks with encrypted secrets and a durable retry queue.
- **Verification**
  - Every Platform read is checked against a proof and every byte against its hash; the CLI and the web app share conformance vectors so they reach the same answer.
  - What is checked, and what is still trusted, is documented in [Check that Forge isn't lying to you](docs/guides/verify-forge.md).
- **Distribution**
  - Prebuilt binaries for Linux (x86_64 and aarch64, glibc; x86_64 static musl), macOS (Intel and Apple silicon) and Windows, with `SHA256SUMS` and GitHub build provenance attestations.
  - `install.sh`, which checks the checksum and, when the GitHub CLI is available, the attestation; `cargo binstall` support.
  - A `forge-relay` container image on GitHub Container Registry.
  - A reproducible IPFS build of the web app, published as a CAR file and CID with each release ([Verify the app you loaded](docs/guides/verify-the-app.md)).
