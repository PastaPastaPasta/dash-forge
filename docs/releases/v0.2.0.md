# Dash Forge v0.2.0

Released TODO(owner): the tagging date. This is the first published release: v0.1.0 was tagged on 2026-10-04 but never published.

Dash Forge is git hosting with no Forge server. Refs, issues, pull requests and access control are documents on Dash Platform, signed by your own identity's keys, and your code lives in storage you choose: your own S3-compatible bucket, an IPFS node, or Platform itself. Every client checks what it reads against Platform proofs and content hashes, so a node, bucket or website cannot make you accept wrong data.

**Forge now runs on testnet.** Its four contracts were registered there on 2026-10-26, and testnet is the default network of every tool, so `dg auth new` needs no flags. The devnet v0.1.0 targeted is down, and nothing on it was carried over.

## Highlights

New since v0.1.0:

- **Testnet.** The production four-contract set (forge-core, forge-collab, forge-community and forge-meta) is registered on testnet, from the same JSON that will be registered on mainnet. forge.dashhq.org, the IPFS build, the guides and the Actions all use it.
- **Members-only content in public repositories.** Issues, comments and reviews that only members read, a reader role, and members-only branches and pull requests, from `dg` and the web app. Everyone else sees that something was posted, by whom and when, never the text. [Who can read what](../security/audiences.md) explains the audiences.
- **Environments** (`dg env`): configuration and secrets kept outside git, encrypted for a repository's maintainers or members, injected with `dg env run`. See [Environments](../guides/environments.md).
- **Secrets in a public push.** `git push` to a public repository refuses a new `.env` file, a private key, an AWS key pair or a GitHub or GitLab token (E807), and warns about likely secrets.
- **Make a private repository public**, once, with `dg repo make-public` or **Settings → Danger zone** in the web app, and **publication dates** for coordinated security fixes (`dg publish --at`, `dg embargo`).
- **Bots and agents (beta).** A Bot role with its own push grants, `dg bot` commands, and forge-runner's agents mode. See [Bots and agents](../guides/bots.md).
- **IPFS you run yourself.** `dg ipfs` installs and supervises a local kubo node and pins and follows repositories; the web app pairs with it and pins a repository's files.
- **Prices in your currency** beside every DASH amount in `dg` and the web app. On testnet they show what the same charge would cost on mainnet.
- **The cost guard asks once per push.** `git push` weighs every pack, index and ref update together before anything is paid, and `dg pr merge --yes` approves the price it showed and no more.
- **More checks you can run.** `dg verify-app` checks a deployed web app file by file against the manifest its build attested, and `dg release verify` checks a release's provenance and signed tag.
- **In the web app:** DPNS usernames, a Devices & keys page with a new-key alert, the mirror wizard split into a GitHub Action path and a command-line path, and an optional HTTPS clone gateway for public repositories ([forge-gateway](../hosting/forge-gateway.md)).

The full list, with the fixes, is in the [changelog](../../CHANGELOG.md).

## Install

**Linux and macOS, with the install script:**

```sh
curl -fsSL https://raw.githubusercontent.com/PastaPastaPasta/dash-forge/v0.2.0/install.sh | DASH_FORGE_VERSION=0.2.0 sh
```

It installs `dg` and `git-remote-dash` into `~/.local/bin`, checks the archive's SHA-256, and checks the build provenance attestation when the GitHub CLI is available ([details](#verify-the-download)). It never runs `sudo`. `DASH_FORGE_BINARIES` adds `forge-relay`, `forge-import` or `forge-runner`, and `DASH_FORGE_COMPLETIONS=1` installs shell completions. Every option is in [INSTALL.md](../INSTALL.md#install-script-linux-and-macos).

**With cargo-binstall** (no checksum or attestation check; it relies on HTTPS):

```sh
cargo binstall --git https://github.com/PastaPastaPasta/dash-forge dg git-remote-dash
```

**By hand:** download your platform's archive and `SHA256SUMS` from the [v0.2.0 release page](https://github.com/PastaPastaPasta/dash-forge/releases/tag/v0.2.0), verify them as [below](#verify-the-download), unpack, and put `dg` and `git-remote-dash` on your `PATH`. On Windows, extract the zip and add the folder to your user `Path`.

**From source:** see [BUILDING.md](../BUILDING.md). You need Rust (pinned by `rust-toolchain.toml`) and `protoc` 25 or newer.

Then check the install and get started:

```sh
dg --version      # dg 0.2.0 (<commit> <target>)
dg doctor         # git, git-remote-dash (same version as dg), network, identity
dg auth new       # an identity on testnet, funded from a faucet
```

The [quick start](../guides/quick-start.md) walks through creating an identity, choosing storage and publishing a repository.

## Verify the download

**Checksum.** In the directory holding the archive and `SHA256SUMS`:

```sh
sha256sum --check --ignore-missing SHA256SUMS          # Linux
shasum -a 256 --check --ignore-missing SHA256SUMS      # macOS
```

On Windows, compare `(Get-FileHash <zip> -Algorithm SHA256).Hash.ToLower()` with the zip's line in `SHA256SUMS`.

**Build provenance.** The archives, the web build and `SHA256SUMS` carry GitHub artifact attestations: Sigstore-signed statements of which workflow built each file, from which commit and tag. There is no project signing key to distribute or leak.

```sh
gh attestation verify dash-forge-0.2.0-<target>.tar.gz --repo PastaPastaPasta/dash-forge
```

Add `--signer-workflow PastaPastaPasta/dash-forge/.github/workflows/release.yml` to also require that the release workflow built it.

The checksum only shows that the download matches `SHA256SUMS`, which comes from the same place. The attestation also shows that both came from this repository's release workflow.

**What `install.sh` checks.** It always checks the archive against `SHA256SUMS` and stops on a mismatch. If the GitHub CLI is installed and logged in, it also runs `gh attestation verify`, requiring the release workflow and the `v0.2.0` tag, and refuses to install if that fails. Without `gh` it says that it skipped the provenance check and prints the command to run yourself. `DASH_FORGE_ATTESTATION=require` makes the attestation check mandatory; `DASH_FORGE_ATTESTATION=skip` relies on the checksum alone.

**macOS.** The binaries are not signed or notarized by Apple. Downloads made by `install.sh`, `curl` or `cargo binstall` are not quarantined and run normally. An archive downloaded in a web browser is quarantined, and Gatekeeper refuses the first run: verify the checksum, then remove the quarantine flag as [INSTALL.md](../INSTALL.md#macos-gatekeeper) shows.

## The web app on IPFS

The release includes the web app as a reproducible IPFS build. Its CID is in the GitHub release notes and in `forge-web-0.2.0.cid`. The release workflow builds it on an x86_64 and an arm64 runner and publishes only if both produce the same CID. This build reads testnet.

Nobody pins this build for you. To run it from your own IPFS node:

```sh
ipfs dag import forge-web-0.2.0.car      # pins the site and prints its root CID
# then open http://<cid>.ipfs.localhost:8080/
```

To check that the app in your browser was built from the `v0.2.0` source, rebuild the CID from the tag (`forge-web/scripts/ipfs-release.sh reproduce v0.2.0 ipfs-build`, which needs git and Docker) and compare it with the release's CID and the CID in the app's footer. [Verify the app you loaded](../guides/verify-the-app.md) has the steps, and says what this does and does not prove. A public gateway does not check the bytes it serves, so load the app through a node you run.

forge.dashhq.org is a separate build of the same source, served by GitHub Pages. `dg verify-app https://forge.dashhq.org` checks it file by file. You can also [build and serve the app yourself](../guides/verify-forge.md#run-your-own-copy-of-the-web-app).

## Known limitations

**Networks and data**

- Testnet only. Mainnet is not supported yet.
- Testnet is a test network: a reset would remove repositories, issues, identities and keys. Keep your clone and your bucket.
- A reset or a contract re-registration can require a new release, because the contract ids are built into each release ([VERSIONING.md](../VERSIONING.md#networks-and-contracts)).
- The landing page features no repositories on testnet yet: the official mirrors are imported and pinned there before the public announcement.

**Installation**

- The macOS binaries are not signed or notarized by Apple ([Gatekeeper](../INSTALL.md#macos-gatekeeper)).
- There is no static build for aarch64 Linux: on glibc older than 2.35, build from source.
- On Windows there is no install script, and `forge-runner` is not included.

**Trust**

- The CLI trusts the one HTTPS endpoint that supplies the validator quorum keys proofs are checked against. It does not yet verify quorums itself (no SPV), and unlike the web app it does not compare the keys with a second source. See [the one trusted input](../guides/verify-forge.md#the-one-trusted-input-quorum-keys). `--quorum-url` points it at a service you trust.
- The web app's checks protect you only if the JavaScript you loaded is the real app. Pin the IPFS build, build it yourself, check the hosted site with `dg verify-app`, or use the CLI.

**Sign-in with Dash Wallet**

- Not available yet. No released Dash Wallet version supports the sign-in, and today's iOS development build pins testnet to protocol 13 while testnet runs 14, so Platform rejects its answer ([#591](https://github.com/PastaPastaPasta/dash-forge/issues/591)). Dash Wallet for Android has not been tried with Forge on testnet. Sign in with an identity file, your 12 words, `dg`, or a new identity created in the browser.
- Once a wallet can answer: keys granted by today's wallets have no spending limit or expiry (the app warns, and offers to replace such a key with a limited one), and a wallet's answer does not prove which identity sent it, so compare the username and identity id with the wallet's approval screen.

Details: [Identity and keys](../guides/identity-and-keys.md#signing-in-with-the-dash-wallet-app-what-works-today).

**Private repositories and members-only content**

- The independent security review of private repositories and members-only content is still open. Treat both as beta until it is published.
- Visible to everyone: that a private repository exists; its name, owner, description and topics; its members and their roles; when pushes, issues, PRs, comments and reviews happen, and who wrote them; commit ids; and sizes. For members-only content in a public repository, everyone also sees a review's verdict.
- Not encrypted in this release: label definitions, check runs and webhook URLs.
- Forks and webhooks are refused on private repositories.
- Removing a member changes the key for future content, but cannot take back what they could already read.
- People on older Forge builds leave members-only items out and do not count members-only approvals, so they may refuse a merge an up-to-date build allows.

The full list is in [Collaborating](../guides/collaborating.md#known-limitations) and [Who can read what](../security/audiences.md).

**Features that still need the CLI**

- Editing files in the browser.
- Some merges: a private repository's pull requests, changes both sides made to the same lines, and merges too large to build in the browser. Use `dg pr merge`.

[Collaborating](../guides/collaborating.md#from-the-web-app) says what the web app does and does not do.

**Compared with GitHub**

- No hosted CI; bring your own runner ([forge-runner](../guides/self-host-runner.md)).
- No wiki, discussions or global search. A shared owner uses an [organization identity](../guides/collaborating.md#organizations).
- No pushing over `https://` and no shallow clones; use `git clone --filter=blob:none`. Read-only `https://` clones of public repositories work through an optional [gateway](../hosting/forge-gateway.md).
- Notifications are computed in your browser unless you use an optional [forge-notify](../hosting/forge-notify.md) service.

[Moving from GitHub or GitLab](../guides/moving-from-github.md#10-github-features-with-no-forge-equivalent) lists every GitHub feature with no equivalent.

**Mirroring**

- After an item is first mirrored, edits to its title or body are not mirrored. Release assets are referenced by their GitHub URL and SHA-256, not re-uploaded. See [the Mirror Action's reference](../../action/README.md#what-is-synced).

**Scripting**

- `--json` output is not stable before 1.0: fields may be added, renamed or removed in a minor release. Pin a version in scripts ([VERSIONING.md](../VERSIONING.md#json-output)).

## Security notes

- **No Forge server.** The project publishes code and static files only. There is no account, database or API to compromise, and no one to ask for your data. The optional gateway and notification services hold no keys and are trusted for availability only.
- **What is checked.** Every Platform read is checked against a proof signed by the validator quorum, and every byte of a pack or release asset against the SHA-256 recorded on Platform. Git checks every object's id. A dishonest node can refuse to answer but cannot forge a proof. A dishonest bucket or gateway can make data unavailable but cannot make a client accept wrong bytes.
- **What is still trusted.** The quorum key endpoint, as described above, and the code doing the checking: the `dg` you installed, or the web app you loaded. Some decisions are rules the Forge apps apply rather than proofs, such as which approvals count and which branch tip wins after a race; the CLI and the web app share conformance vectors so they apply them identically. [Check that Forge isn't lying to you](../guides/verify-forge.md) is precise about all of this.
- **Keys.** Day-to-day signing uses limited keys: a budget, an expiry, and usable only on Forge's contracts, enforced by Platform. The CLI keeps its key in the OS keychain or a passphrase-sealed file, and the browser in an encrypted vault unlocked by a passkey or passphrase. The master key signs only one-time steps and is not stored unless you ask for it. [Identity and keys](../guides/identity-and-keys.md) explains backup and recovery: lose your 12 recovery words and every identity file, and nobody can recover the identity.
- **The web app's scripts.** In production each page allows only its own inline scripts, by hash, so a script a host injects into the HTML does not run beside the key vault.
- **Supply chain.** Release files carry Sigstore build provenance attestations from GitHub Actions, and the web app's IPFS build is reproducible from the tag.
- **No moderation in the contracts.** Forge's contracts are registered without Platform's contract moderation: nobody, including the Forge project, can delete your documents or ban your identity. Within a repository, members can lock a thread to non-members and maintainers can hide posts. forge.dashhq.org can hide repositories from its own lists ([hosted curation](../hosted-curation.md)); they stay on Platform and `dash://` still works.
- **Reporting a vulnerability.** Please report security issues privately through a [GitHub security advisory](https://github.com/PastaPastaPasta/dash-forge/security/advisories/new), not in a public issue.

## Upgrading

**From a source build or v0.1.0.** Install this release over the old binaries; `dg doctor` reports a `git-remote-dash` whose version does not match `dg`. Your configuration in `~/.config/dash-forge` and the keys in your keychain are left as they are.

**From the devnet.** Nothing on the devnet v0.1.0 targeted was carried over to testnet: identities, repositories, issues and keys there are gone. Your git clones and your own storage are kept.

1. If you had recorded the devnet as your default, select testnet once: `dg auth new --network testnet` (or `dg auth login --network testnet …`) records it as the default again.
2. Remove a devnet you set in git config (`dash.network`, `dash.devnetName`), globally and in each clone.
3. Re-push each repository from its clone with `dg init` (`dg init --private` for a private one), and set mirrors up again with the /mirror wizard.

[Dash Forge moved to testnet](../guides/devnet-move.md) has the commands.

**Workflows.** A Mirror Action or check action step that set `network: devnet` and a `devnet-name` must drop both (the default is testnet), and its `DASH_FORGE_KEY` must be a key for your testnet identity. If a workflow uses the actions at `@master`, pin `@v0.2.0` instead, or a reviewed commit with `install: 'source'`.

What changed is in [CHANGELOG.md](../../CHANGELOG.md). How version numbers work, and what may change in a 0.x minor release, is in [VERSIONING.md](../VERSIONING.md).
