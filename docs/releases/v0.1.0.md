# Dash Forge v0.1.0

Released 2026-10-04. This is the first release.

Dash Forge is git hosting with no Forge server. Refs, issues, pull requests and access control are documents on Dash Platform, signed by your own identity's keys, and your code lives in storage you choose: your own S3-compatible bucket, an IPFS node, or Platform itself. Every client checks what it reads against Platform proofs and content hashes, so a node, bucket or website cannot make you accept wrong data.

## Highlights

- **Plain git over `dash://`.** `git clone dash://<owner>/<name>` and `git push` work unchanged through the `git-remote-dash` helper, and so does jj. Every push prints its cost before it pays.
- **`dg`, a `gh`-shaped CLI** for repositories, forks, issues, pull requests, reviews, real merges, releases, members, storage, webhooks and check runs. `dg init` publishes an existing repository in one step.
- **Bring your own storage.** Packs go to R2, B2, AWS S3, Storj, a self-hosted S3 store, IPFS, or Platform, with N-of-M replication. Readers accept only bytes that match the SHA-256 recorded on chain.
- **Limited keys.** The CLI and the web app sign with keys that have a budget, an expiry, and work only on Forge's contracts, enforced by Platform. The master key is used for one-time steps and not stored.
- **Collaboration.** Reader, triage, writer and maintainer roles enforced at consensus; protected branches; branch policies; code owners; pull requests from branches or forks; merges by fast-forward, merge commit, squash or rebase.
- **Private repositories**, encrypted on your machine to the members' keys. Removing a member rotates the key.
- **A web app with no backend** at [forge.dashhq.org](https://forge.dashhq.org), with a Verification card on every repository page, and a reproducible IPFS build you can pin yourself.
- **Mirror GitHub or GitLab.** `forge-import`, the Mirror Action and a GitLab CI template keep a copy that nobody can take down, under a cost cap.
- **CI without a CI service.** Check runs signed by runner keys that can sign nothing else, `forge-runner` for self-hosted workflows, the check action for GitHub Actions, and `forge-relay` for GitHub-shaped webhooks.

The full list is in the [changelog](../../CHANGELOG.md).

## Networks

| Network | Supported in v0.1.0 |
|---|---|
| **Devnet sakura** (Dash Platform v5.0.0-beta.1, protocol 14, chain id `dash-devnet-sakura`) | **Yes.** Forge's three contracts (forge-core, forge-collab, forge-community) are registered here in one contract group. The hosted web app at [forge.dashhq.org](https://forge.dashhq.org) runs on sakura. Test Dash comes from the [sakura faucet](https://faucet.sakura.networks.dash.org). |
| **Testnet** | No. Testnet runs protocol 13. Forge is registered there once protocol 14 reaches it. |
| **Mainnet** | No. The forge-v2 contracts are registered on mainnet after protocol 14 activates there ([runbook](../mainnet-runbook.md)). |

On a network without a Forge deployment, `dg`, `git-remote-dash` and the web app stop with a "not deployed" error ([E702](../errors.md#e702)).

**Treat data on a devnet as disposable.** A devnet can be wiped or retired. Two earlier devnets already were, and everything on them (repositories, issues, identities and keys) went with them. Keep your git clone, and keep your own storage bucket: both survive a devnet reset, and you can re-push from the clone. [Dash Forge moved to devnet sakura](../guides/devnet-move.md) describes the last move.

The CLI's default network is testnet, so select sakura the first time: `dg auth new --network devnet --devnet-name sakura` (or `dg auth login … --network devnet --devnet-name sakura`) records it as your default.

## Install

**Linux and macOS, with the install script:**

```sh
curl -fsSL https://raw.githubusercontent.com/PastaPastaPasta/dash-forge/v0.1.0/install.sh | DASH_FORGE_VERSION=0.1.0 sh
```

It installs `dg` and `git-remote-dash` into `~/.local/bin`, checks the archive's SHA-256, and checks the build provenance attestation when the GitHub CLI is available ([details](#verify-the-download)). It never runs `sudo`. `DASH_FORGE_BINARIES` adds `forge-relay`, `forge-import` or `forge-runner`, and `DASH_FORGE_COMPLETIONS=1` installs shell completions. Every option is in [INSTALL.md](../INSTALL.md#install-script-linux-and-macos).

**With cargo-binstall** (no checksum or attestation check; it relies on HTTPS):

```sh
cargo binstall --git https://github.com/PastaPastaPasta/dash-forge dg git-remote-dash
```

**By hand:** download your platform's archive and `SHA256SUMS` from the [v0.1.0 release page](https://github.com/PastaPastaPasta/dash-forge/releases/tag/v0.1.0), verify them as [below](#verify-the-download), unpack, and put `dg` and `git-remote-dash` on your `PATH`. On Windows, extract the zip and add the folder to your user `Path`.

**From source:** see [BUILDING.md](../BUILDING.md). You need Rust (pinned by `rust-toolchain.toml`) and `protoc` 25 or newer.

Then check the install and get started:

```sh
dg --version      # dg 0.1.0 (<commit> <target>)
dg doctor         # git, git-remote-dash (same version as dg), network, identity
```

The [quick start](../guides/quick-start.md) walks through creating an identity, choosing storage and publishing a repository.

Each archive holds one directory, named like the archive, containing:

**Container image:** `ghcr.io/pastapastapasta/forge-relay:0.1.0`, also tagged `:latest`, built from the checksummed static Linux archive. [Running a relay](../../crates/forge-relay/README.md) explains how to use it.

**GitHub Actions.** Pin the actions to this release's tag:

- The Mirror Action: `uses: PastaPastaPasta/dash-forge/action@v0.1.0`. At this tag the action's default `version` is `0.1.0`, so `install: 'true'` downloads the release binaries above, checked against `SHA256SUMS` and the attestation, instead of compiling them. `install: 'source'` still builds from the action's own source. See [the Mirror Action's reference](../../action/README.md) and [Mirror a GitHub repository](../guides/mirror-a-github-repo.md).
- The check action: `uses: PastaPastaPasta/dash-forge/check-action@v0.1.0`, which installs the release's `dg` the same way. See [the check action's reference](../../check-action/README.md) and [CI and check runs](../guides/ci.md).

## Verify the download

**Checksum.** In the directory holding the archive and `SHA256SUMS`:

```sh
sha256sum --check --ignore-missing SHA256SUMS          # Linux
shasum -a 256 --check --ignore-missing SHA256SUMS      # macOS
```

On Windows, compare `(Get-FileHash <zip> -Algorithm SHA256).Hash.ToLower()` with the zip's line in `SHA256SUMS`.

**Build provenance.** The archives, the web build and `SHA256SUMS` carry GitHub artifact attestations: Sigstore-signed statements of which workflow built each file, from which commit and tag. There is no project signing key to distribute or leak.

```sh
gh attestation verify dash-forge-0.1.0-<target>.tar.gz --repo PastaPastaPasta/dash-forge
```

Add `--signer-workflow PastaPastaPasta/dash-forge/.github/workflows/release.yml` to also require that the release workflow built it.

The checksum only shows that the download matches `SHA256SUMS`, which comes from the same place. The attestation also shows that both came from this repository's release workflow.

**What `install.sh` checks.** It always checks the archive against `SHA256SUMS` and stops on a mismatch. If the GitHub CLI is installed and logged in, it also runs `gh attestation verify`, requiring the release workflow and the `v0.1.0` tag, and refuses to install if that fails. Without `gh` it says that it skipped the provenance check and prints the command to run yourself. `DASH_FORGE_ATTESTATION=require` makes the attestation check mandatory; `DASH_FORGE_ATTESTATION=skip` relies on the checksum alone.

**macOS.** The binaries are not signed or notarized by Apple. Downloads made by `install.sh`, `curl` or `cargo binstall` are not quarantined and run normally. An archive downloaded in a web browser is quarantined, and Gatekeeper refuses the first run: verify the checksum, then remove the quarantine flag as [INSTALL.md](../INSTALL.md#macos-gatekeeper) shows.

## The web app on IPFS

The release includes the web app as a reproducible IPFS build. Its CID is in the GitHub release notes and in `forge-web-0.1.0.cid`. The release workflow builds it on an x86_64 and an arm64 runner and publishes only if both produce the same CID. This build reads devnet sakura.

Nobody pins this build for you. To run it from your own IPFS node:

```sh
ipfs dag import forge-web-0.1.0.car      # pins the site and prints its root CID
# then open http://<cid>.ipfs.localhost:8080/
```

To check that the app in your browser was built from the `v0.1.0` source, rebuild the CID from the tag (`forge-web/scripts/ipfs-release.sh reproduce v0.1.0 ipfs-build`, which needs git and Docker) and compare it with the release's CID and the CID in the app's footer. [Verify the app you loaded](../guides/verify-the-app.md) has the steps, and says what this does and does not prove. A public gateway does not check the bytes it serves, so load the app through a node you run.

forge.dashhq.org is a separate build of the same source, served by GitHub Pages. You can also [build and serve the app yourself](../guides/verify-forge.md#run-your-own-copy-of-the-web-app).

## Known limitations

**Networks and data**

- Devnet sakura only. Testnet and mainnet are not supported yet.
- Data on a devnet is disposable: a reset or retirement removes repositories, issues, identities and keys. Keep your clone and your bucket.
- A devnet reset or a contract re-registration can require a new release, because the contract ids are built into each release ([VERSIONING.md](../VERSIONING.md#networks-and-contracts)).

**Installation**

- The macOS binaries are not signed or notarized by Apple ([Gatekeeper](../INSTALL.md#macos-gatekeeper)).
- There is no static build for aarch64 Linux: on glibc older than 2.35, build from source.
- On Windows there is no install script, and `forge-runner` is not included.
- The CLI's default network is testnet, where Forge is not deployed. Select sakura once, as shown in [Networks](#networks).

**Trust**

- The CLI trusts the HTTPS endpoint that supplies the validator quorum keys proofs are checked against. It does not yet verify quorums itself (no SPV). The web app compares those keys with a second source on every repository page; the CLI does not yet. See [the one trusted input](../guides/verify-forge.md#the-one-trusted-input-quorum-keys).
- The web app's checks protect you only if the JavaScript you loaded is the real app. Pin the IPFS build, build it yourself, or use the CLI.

**Sign-in with Dash Wallet**

- No released Dash Wallet version supports the sign-in yet. On sakura, only an internal iOS build pointed at Forge's key-exchange contract by hand can answer, and that has not been tried on a real device. Dash Wallet for Android refuses requests off testnet.
- Keys granted by today's wallets have no spending limit or expiry. The app warns, and offers to replace such a key with a limited one.
- A wallet's answer does not prove which identity sent it. Compare the username and identity id with the wallet's approval screen.

Details: [Identity and keys](../guides/identity-and-keys.md#signing-in-with-the-dash-wallet-app-what-works-today).

**Private repositories**

- Visible to everyone: that the repository exists; its name, owner, description and topics; its members and their roles; when pushes, issues, PRs, comments and reviews happen, and who wrote them; commit ids; and sizes.
- Not encrypted in this release: label definitions, check runs and webhook URLs.
- Not supported yet on private repositories: forks, webhooks and milestones.
- Removing a member rotates the key for future content, but cannot take back what they could already read.

The full list is in [Collaborating](../guides/collaborating.md#private-repositories).

**Features that still need the CLI**

- Some merges need `dg pr merge`, not the browser:
  - a private repository's pull requests;
  - changes where both sides edited the same lines, or one side renamed or deleted what the other changed;
  - binary files, files over 2 MiB, and files under a `.gitattributes`;
  - merges too large to build in the browser.
- Not yet in the browser: editing files, committing to a private repository's branches, deleting tags, locking a pull request, and syncing a fork whose branch has commits of its own.
- The CLI does not read issue and PR templates, and does not show a mirrored item's upstream number.
- Only maintainers and writers can post a text over 5,120 bytes; triage members, readers and non-members are held to that limit. Long text is not yet supported in `dg pr review` drafts, the web's inline review comments, or a private repository's release notes written on the web (use `dg release create`).
- Code owners are asked for review, but "require review from code owners" is not available as a branch rule.

**Compared with GitHub**

- No hosted CI; bring your own runner.
- No wiki, discussions, organization accounts, reactions or global search. A shared owner uses an [organization identity](../guides/collaborating.md#organizations).
- No `https://` clone URLs and no shallow clones; use `git clone --filter=blob:none`.
- Notifications are computed in your browser: no email, no push notifications, and no sync across devices.

**Mirroring**

- After an item is first mirrored, edits to its title or body are not mirrored, and neither is a PR moved to another base branch.
- Milestones, assignees, reactions, projects, discussions, the wiki and Actions artifacts are not mirrored.
- Release assets are referenced by their GitHub URL and SHA-256, not re-uploaded.

See [the Mirror Action's reference](../../action/README.md#what-is-synced).

**Scripting**

- `--json` output is not stable before 1.0: fields may be added, renamed or removed in a minor release. Pin a version in scripts ([VERSIONING.md](../VERSIONING.md#json-output)).

## Security notes

- **No Forge server.** The project publishes code and static files only. There is no account, database or API to compromise, and no one to ask for your data.
- **What is checked.** Every Platform read is checked against a proof signed by the validator quorum, and every byte of a pack or release asset against the SHA-256 recorded on chain. Git checks every object's id. A dishonest node can refuse to answer but cannot forge a proof. A dishonest bucket or gateway can make data unavailable but cannot make a client accept wrong bytes. A webhook relay is trusted for availability only.
- **What is still trusted.** The quorum key endpoint, as described above, and the code doing the checking: the `dg` you installed, or the web app you loaded. Some decisions are client rules rather than proofs, such as which approvals count and which branch tip wins after a race; the CLI and the web app share conformance vectors so they apply them identically. [Check that Forge isn't lying to you](../guides/verify-forge.md) is precise about all of this.
- **Keys.** Day-to-day signing uses limited keys: a budget, an expiry, and usable only on Forge's contracts, enforced at consensus. The CLI keeps its key in the OS keychain (macOS Keychain, Secret Service, Windows Credential Manager) or a passphrase-sealed file. The browser keeps its key in an encrypted vault unlocked by a passkey or passphrase. The master key signs only one-time steps and is not stored unless you ask for it (`dg auth login --full-key`, which writes a passphrase-sealed file). CI gets runner keys that can sign only check runs, or a limited `dfk1:` key. [Identity and keys](../guides/identity-and-keys.md) explains backup and recovery: lose your 12 recovery words and every identity file, and nobody can recover the identity.
- **Supply chain.** Release files carry Sigstore build provenance attestations from GitHub Actions, and the web app's IPFS build is reproducible from the tag.
- **No moderation in the contracts.** Forge's contracts are registered without Platform's contract moderation: nobody, including the Forge project, can delete your documents or ban your identity. Within a repository, members can lock a thread to non-members and maintainers can hide posts; hidden posts stay readable to anyone who asks.
- **Reporting a vulnerability.** Please report security issues privately through a [GitHub security advisory](https://github.com/PastaPastaPasta/dash-forge/security/advisories/new), not in a public issue.

## Upgrading

This is the first release, so there is nothing to migrate from an earlier one. If you built `dg` and `git-remote-dash` from source before, install the release over them; `dg doctor` reports a `git-remote-dash` whose version does not match `dg`. Your configuration in `~/.config/dash-forge` and the keys in your keychain are left as they are.

If a workflow uses the Mirror Action or the check action at `@master`, it now downloads the latest release's binaries instead of building from source. Pin `@v0.1.0` instead, or a reviewed commit with `install: 'source'`.

Identities, repositories and keys from devnets Forge has left are gone; re-push from your clone as [Dash Forge moved to devnet sakura](../guides/devnet-move.md) describes.

What changed is in [CHANGELOG.md](../../CHANGELOG.md). How version numbers work, and what may change in a 0.x minor release, is in [VERSIONING.md](../VERSIONING.md).
