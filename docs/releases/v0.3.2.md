# Dash Forge v0.3.2

Released 2026-11-27.

**`dg` syncs your settings on mainnet, and you can move sync to a new key.** forge-user, the contract that keeps your storage settings encrypted on Platform, was registered on mainnet after v0.3.1 was cut. `dg` builds the contracts it trusts in at compile time, so v0.3.1 doesn't know mainnet's forge-user. It keeps mainnet storage settings on each computer, and `--strict-group` refuses mainnet's contract group because of the member it doesn't know. v0.3.2 knows it: on mainnet, as on testnet, `dg auth login --wallet` turns sync on, and `--strict-group` accepts the group.

## What changed

- **Settings that follow your identity, on mainnet** ([#750](https://github.com/PastaPastaPasta/dash-forge/pull/750)). After `dg auth login --wallet` on mainnet, your storage profiles (credentials included) and your default storage follow your identity to every computer and browser where you sign in with the same wallet, and an owner can share a repository's storage with its maintainers (`dg storage share`). `dg doctor` has a `settings sync` row. How it works and what a leaked sync key means: [Identity and keys](../guides/identity-and-keys.md#settings-that-follow-your-identity).
- **Move settings sync to a new key** ([#751](https://github.com/PastaPastaPasta/dash-forge/issues/751), [#766](https://github.com/PastaPastaPasta/dash-forge/pull/766)). A site that tricks you into approving a wallet code gets your settings-sync key, and every wallet sign-in hands out the same one. `dg storage sync move-key` (and **Settings → Storage → Move sync to a new key** in the web app) makes the next key from your recovery phrase, registers it, disables the old one, and encrypts your synced settings and repository shares again under it. Other computers add it once with `dg storage sync add-key`. After a move, wallet sign-ins no longer carry the sync key, and a computer still holding the old key, v0.3.1 included, stops syncing until it adds the new one. The steps: [If a site may have your settings-sync key](../guides/rotate-storage-credentials.md#if-a-site-may-have-your-settings-sync-key).
- **`--strict-group` on mainnet** accepts Forge's contract group again, now that dg knows every member, forge-user included.
- **Wallet renewals** say which identity they renew, and `--any-identity` lets another identity in the wallet answer. A renewal no longer asks about a master-key file it doesn't touch ([#764](https://github.com/PastaPastaPasta/dash-forge/pull/764)).
- **`dg auth logout` keeps a copy of a master key** (`<name>.bak-<UTC time>`) instead of deleting it, and a wallet sign-in on a computer whose keychain fails keeps the settings-sync key in a sealed file ([#771](https://github.com/PastaPastaPasta/dash-forge/pull/771)).
- **Clearer hints**: a `dash://` name that doesn't resolve now names the network fix for both `dg` and plain git; a fresh install no longer says "sign in with your wallet again" ([#765](https://github.com/PastaPastaPasta/dash-forge/pull/765)).

Nothing else changed in the tools. Everything in [v0.3.1](v0.3.1.md) still applies.

## Upgrading from v0.3.1

Install v0.3.2 over v0.3.1 the usual way (below). Nothing needs migrating: v0.3.2 reads v0.3.1's config file, stored keys and key backups as they are, and does not rewrite them.

**Mainnet settings.** The first `dg auth login --wallet` on mainnet with v0.3.2 turns sync on for that computer. The first sync uploads the storage profiles and default storage this computer has and keeps `storage.toml` as it is ([how the merge works](../guides/identity-and-keys.md#settings-that-follow-your-identity)). Each sync is a Platform write paid from your key's budget, in real DASH on mainnet; if your wallet rejects the code, `dg auth login --wallet --no-sync` signs in without sync. Until you sign in with your wallet again, v0.3.2 keeps mainnet settings on this computer, as v0.3.1 did.

**Workflows.** Pin the Mirror Action and the check action to `@v0.3.2`.

## Known limitations

- The limitations listed for [v0.3.1](v0.3.1.md#known-limitations) still apply, except that settings that follow your identity now work on mainnet in `dg` too. Organizations are still testnet only.

## Install and verify

Install, verification and the IPFS build work as in [v0.2.0](v0.2.0.md#install), with `0.3.2` in place of `0.2.0`. Release binaries are built for Linux (x86_64 and arm64, plus a static x86_64 musl build), macOS (Intel and Apple silicon) and Windows (x86_64). `SHA256SUMS` lists every file, and each file has a GitHub build-provenance attestation.

What changed is in [CHANGELOG.md](../../CHANGELOG.md). How version numbers work is in [VERSIONING.md](../VERSIONING.md).
