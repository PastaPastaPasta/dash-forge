# Dash Forge v0.3.0

Released 2026-11-26.

> **Use [v0.3.1](v0.3.1.md) on testnet.** Testnet moved to protocol 15 on 2026-11-25, before this release was published, and much of v0.3.0 fails there. The testnet rows below describe protocol 14.

**Forge is on Dash mainnet, and this is the first `dg` that can use it.** Forge's contracts were registered on mainnet on 2026-11-24, and [forge.dashhq.org](https://forge.dashhq.org) has served mainnet since then. v0.3.0 is the first release whose command-line tools know those contracts: v0.2.0 stops on mainnet with "not deployed". Testnet stays live, at [testnet-forge.dashhq.org](https://testnet-forge.dashhq.org), and it is still the tools' default network.

**Mainnet DASH is real money, and there is no faucet.** Every write costs real credits, paid by your own identity. Forge's tools show the price, in DASH and in your currency, before they spend anything.

## Using mainnet from the command line

Testnet stays the default, so nothing you set up with v0.2.0 moves to mainnet by itself. To use mainnet:

- **For one command:** add `--network mainnet`.
- **As your default:** sign in on mainnet once. `dg auth login --network mainnet` (with your DashPay wallet, an identity file or a recovery phrase) or `dg auth new --network mainnet` records mainnet as your default, for `dg` and for plain `git clone` and `git push`.
- **In a clone:** a clone made by `dg repo clone` or `dg init` remembers its network, so `dg` and `git push` inside it stay on that network whatever your default is. They still sign with your default identity, though: see [Using testnet and mainnet side by side](#using-testnet-and-mainnet-side-by-side).
- **In CI:** set `network: mainnet` in the Mirror Action or the check action (`FORGE_NETWORK: mainnet` in the GitLab template), with a `DASH_FORGE_KEY` for your mainnet identity.

`git push` also follows `DASH_FORGE_NETWORK` and git config `dash.network`, ahead of your recorded default. `dg` reads its recorded default first, and now warns when it ignores a `DASH_FORGE_NETWORK` that names another network.

**Funding.** A mainnet identity needs DASH from a wallet you control. The easiest way is DashPay: create your identity there, buy credits there, and sign in to Forge with it. `dg` prints the top-up link for the network you are on.

### Using testnet and mainnet side by side

`dg` keeps one default: one network and one identity. Signing in on mainnet replaces your testnet default (your testnet key stays stored, untouched). After that:

- **A clone that doesn't record its network** (a plain `git clone dash://…`, or one made by a build before v0.2.0) follows the default, so its `git push` goes to mainnet. Run `git config dash.network testnet` in each such clone first.
- **A testnet clone signs with your default identity**, now the mainnet one, so a push there is refused ([E304](../errors.md#e304)). For testnet, pass your testnet key for that command: `DASH_FORGE_KEY=keychain:dash-forge/testnet/<identity id> git push` (or the key file, `~/.config/dash-forge/identities/testnet-<identity id>.key`), or `--identity` with `dg`. Signing in on testnet again makes testnet the default again. Don't follow a hint to set `dash.network mainnet` in a testnet clone.

**A mainnet identity is separate from your testnet one.** Your testnet identity, keys and repositories do not exist on mainnet. To publish a repository on mainnet too, push it from a separate copy of your clone: `git clone <your clone> <name>-mainnet`, then in the copy `git fetch --update-head-ok origin 'refs/heads/*:refs/heads/*'` (so every branch comes along, not only the checked-out one), `git remote remove origin` and `dg init --network mainnet`.

## Highlights

New since v0.2.0:

- **Mainnet**, as above. Links that `dg` prints and the storage CORS check now follow the network: testnet points at testnet-forge.dashhq.org, mainnet at forge.dashhq.org. The top-up link opens the bridge on your network (`bridge.thepasta.org/?network=…`).
- **Sign in with your DashPay wallet.** `dg auth login` with no file shows a QR code and a `dashpay://connect` link. Scan it in DashPay, approve, and the wallet gives `dg` a limited key with a spending cap and an expiry. The web app's sign-in is now two choices: your wallet, or a passkey. On mainnet, no everyday screen asks for your recovery phrase. `dg auth status` and the web app's Settings say where your key came from.
- **A narrower key for CI.** `dg auth export --new-key --scope core` makes a limited key that only works on forge-core, which is enough for a job that mirrors code and releases. It is not a code-only key: a leaked one can still add maintainers, change settings and create or delete repositories, and it can't create private repositories.
- **Pin or fork onto your own storage.** `dg repo pin <owner>/<name>` (or **Pin** on the repo page) copies a repository's packs to your IPFS node or bucket and records where they are, so clones still work if the original storage disappears. `dg repo fork` now copies the packs too, instead of pointing at the parent's storage.
- **Your own storage backend in one command.** `backend.sh` turns a Linux machine with Docker (a NAS, PC or server) into storage your repositories push to. See [Run your own storage backend](../guides/self-host-backend.md).
- **Faster reads.** Pack reads try Forge's own IPFS gateway first with fewer, larger requests, and the web app can fetch packs straight from IPFS peers in the browser, with the gateways as a fallback. Every byte is still checked against its hash.
- **Pull requests:** `dg pr diff` works outside a clone and shows what a merged pull request brought in.
- **Clearer errors:** `dg` says when `git-remote-dash` is missing before it runs git, `dg repo view` explains a security policy it couldn't check, and `dg ipfs up` and `dg ipfs connect` print the link and code instead of opening a browser (`--open` opens it). The web app connects a local IPFS node on the first try.
- **A calmer web app:** shorter screens, repository Settings with one section at a time, progress for every Platform write, and three steps for an empty repository's first push.

The full list is in the [changelog](../../CHANGELOG.md).

## Testnet only for now

Two new features ship in these binaries but work on testnet only:

- **Settings and storage that follow your identity.** Your storage profiles and preferences are encrypted and kept with your identity, so another computer or browser signed in as you gets them, and a repository owner can share the repository's storage with its maintainers. It needs the forge-user contract, which is registered on testnet only. It comes to mainnet in **v0.4.0**.
- **Organizations.** A repository can be owned by a group of people, where a set number of them must sign each owner action (`dg org`). It is switched off on mainnet until a later release.

On mainnet both stay off: nothing is synced and no org commands write. Your local `storage.toml` keeps working as before.

## Upgrading from v0.2.0

Install v0.3.0 over the old binaries, and update `dg` and `git-remote-dash` together. Your configuration, keys, clones and repositories keep working:

- `~/.config/dash-forge` (config.toml, your stored keys, storage profiles) is read as it is. Nothing is converted, so v0.2.0 can still read it if you go back.
- A key stored by v0.2.0 keeps working. `dg auth status` shows where it came from as "the OS keychain (stored by an earlier dg)", or "not recorded" for a key file.
- Testnet stays your default. Clones keep the network they recorded.
- Repositories, issues and pull requests written by v0.2.0 read the same in v0.3.0, and the other way round.

**A key `dg` replaces is kept.** When you sign in again or renew, `dg` first copies the key it stored for that identity, a master key included: the key file to `<network>-<id>.key.bak-<UTC time>` beside it, or the keychain entry to one named `….bak-<UTC time>`. It says where the copy went, and never writes over an earlier copy. `--identity <copy>` uses it. `dg auth logout` doesn't remove these copies, and one may hold your master key: delete the ones you no longer need.

Two changes might affect scripts:

- **A bare `dg auth login` now signs in with your wallet.** Without a terminal (or with `--json`) it stops with [E802](../errors.md#e802) (exit 8) instead of a usage error, and stores nothing. Scripts should pass an identity file, use `--wallet --yes`, or set `DASH_FORGE_KEY`.
- **The web app's older wallet code (v1 DashConnect) is gone.** Wallet sign-in uses App Connect v2. Keys the older code gave a browser still work there.

**Bookmarks.** forge.dashhq.org shows mainnet. Testnet repositories are at testnet-forge.dashhq.org, which is a separate site, so a passkey made at forge.dashhq.org for a testnet identity doesn't work there. Sign in with your wallet, identity file or recovery phrase instead.

**Your own storage.** If the testnet web app reads your bucket or IPFS node, allow `https://testnet-forge.dashhq.org` as well as `https://forge.dashhq.org`: add it to the bucket's CORS allowed origins, or run `dg ipfs origin add https://testnet-forge.dashhq.org` for a paired node.

**Workflows.** Pin `@v0.3.0`. A workflow for a mainnet repository sets `network: mainnet`.

## Known limitations

- **One default identity per computer.** Signing in on another network replaces the default, as above; use `DASH_FORGE_KEY` or `--identity` for the other network.
- **Testnet only:** settings and storage that follow your identity, and organizations (see above).
- **Mainnet costs real DASH**, and the tools' prices are estimates until the write is made. Set a key's budget (`--budget`) to what you are willing to spend.
- The limitations listed for [v0.2.0](v0.2.0.md#known-limitations) still apply, except those about mainnet.

## Install and verify

Install, verification and the IPFS build work as in [v0.2.0](v0.2.0.md#install), with `0.3.0` in place of `0.2.0`. Release binaries are built for Linux (x86_64 and arm64, plus a static x86_64 musl build), macOS (Intel and Apple silicon) and Windows (x86_64). `SHA256SUMS` lists every file, and each file has a GitHub build-provenance attestation.

What changed is in [CHANGELOG.md](../../CHANGELOG.md). How version numbers work is in [VERSIONING.md](../VERSIONING.md).
