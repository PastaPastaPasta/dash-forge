# Deploying Forge to a network

**For the person who registers Forge's contracts on a network: testnet first, then mainnet.** The steps are the same on both; where they differ, this page says so.

Registration is the one step in a Forge launch that cannot be undone. Contracts cannot be deleted, re-owned or changed beyond additive updates ([after registration](#7-after-registration-what-can-still-change)). Rehearse it on a scratch set first, and read this page to the end before you broadcast anything.

**Status.** Forge is registered on devnet sakura only. A network has a Forge deployment once `forge-contracts/deployments/<network>.json` holds a complete `v2` record; testnet's and mainnet's files hold only the network's addresses and chain id until the registration commit lands. Until then every client reports "not deployed" on that network ([E702](errors.md#e702)) and never falls back to another network's ids. [Networks](networks.md) says what runs where.

## 1. What is registered

Four contracts, in one contract group (`dash-forge`) that has an owner and **no admins**:

| Order | Contract | What it holds |
|---|---|---|
| 1 | `forge-core` | repositories, members, packs, refs, releases, config. Its create transition also creates the contract group. |
| 2 | `forge-collab` | issues, pull requests, reviews, comments, transitions |
| 3 | `forge-community` | stars, events, profiles, check runs, policies, runners |
| 4 | `forge-meta` | the fourth contract of the production set ([forge-v2.md §2](contracts/forge-v2.md#forge-meta-mainnet-set-only)) |

The order is fixed. Each contract takes the deployer's next identity nonce, the contract and group ids derive from those nonces, and each later contract's schema names the ids of the ones registered before it. [forge-v2.md §8](contracts/forge-v2.md#8-deploying) has the details.

**Use the production set, not the devnet files.** There are two committed sets:

| Set | Directory | Contracts | Used on |
|---|---|---|---|
| `devnet` | `forge-contracts/contracts/` | three (no forge-meta) | devnets such as sakura |
| `mainnet` | `forge-contracts/contracts/mainnet/` | four | **testnet and mainnet** |

The `mainnet` set is generated by `python3 forge-contracts/schema/build.py --mainnet --out <dir>` and committed; CI's `build.py --check` keeps the committed files equal to a fresh build. Testnet and mainnet always need `--set mainnet` in `deploy-v2.mjs`, and a record remembers the set it was registered from (`v2.contractsSet`), so a four-contract record can never be updated from the three-contract files.

A group-bound key can sign for every member of the group ([Contract group trust](contracts/forge-v2.md#contract-group-trust)), so clients pin the group's owner and refuse a group with admins. Never register one.

## 2. Before you register

All of these come first. `deploy-v2.mjs` enforces the ones it can; the rest are on you.

1. **The platform pin.** `forge-contracts/sdk-v2/package.json` pins the SDK the script uses (`@dashevo/evo-sdk` 5.0.0-rc.3 today); the clients, `dg` and the web app, pin the same release. Run `(cd forge-contracts/sdk-v2 && npm ci)`. The script refuses to broadcast unless the network runs protocol 14 (`PROTOCOL_VERSION` in `deploy-v2.mjs`).
2. **Freeze the schema.** Rules, indexes and config freeze at registration ([§7](#7-after-registration-what-can-still-change)). Decide `config.readonly` (it can only be set at registration; Forge registers writable so later additive updates can land) and every other now-or-never choice, and merge the schema to `master`. The script refuses to register files that differ from git `HEAD`, a `HEAD` that is not on a branch of `origin`, or a committed set that `build.py --check` rejects.
3. **Rehearse on a scratch set.** Register the same committed JSON under a throwaway deployer and run the live suites against it, on the same network and the same Platform release. A scratch registration is permanent too, so use a different deployer from the real one:

   ```bash
   node forge-contracts/scripts/deploy-v2.mjs --network testnet --set mainnet \
        --identity <scratch-deployer.identity.json> \
        --record <scratch-record.json> --scratch-on testnet [--dry-run]
   ```

   `--record` must be outside `forge-contracts/deployments/`; `--scratch-on <network>` must equal `--network` and is required on testnet and mainnet. The script refuses it when the deployer is any identity the live `deployments/<network>.json` names, and a scratch record that names the network's own forge-core or group.
4. **Sign the sums.** `node forge-contracts/scripts/deploy-v2.mjs --print-sha256 --set mainnet` prints `sha256sum` lines for the set's files (every `--dry-run` prints them too). The owner signs exactly those lines after the rehearsal passes; they are the input to `--expect-sha256`. Registering into the live testnet or mainnet record is refused unless every file matches the signed sums.
5. **Size headroom.** Every create transition must leave at least 2,000 bytes under the network's `max_state_transition_size` (20,480). The dry run prints each transition's size and checks it.
6. **Chain id.** The script proves the chain id (a DPNS proof that agrees with the node's status) and requires the network's own (`dash-testnet-<n>`, or the mainnet one). It records it, and a later run against another chain stops.
7. **Fresh DAPI seeds.** `node forge-contracts/scripts/refresh-dapi.mjs --network <network> --check` probes the recorded `dapiAddresses`; `--write` rebuilds them from the quorum service so they hold only nodes that run protocol 14 and are at the chain tip.

## 3. Deployer custody

The deployer owns the contracts and the group, and only the owner can update the contracts. Contract owners are immutable, so custody of this identity is the only succession mechanism, and the only way to restore the same ids after a Platform reset.

- **A fresh, dedicated, owner-held deployer.** Create it from a new mnemonic on a machine the owner controls (`tools/mint-identity/mint.mjs`, [README](../tools/mint-identity/README.md)); never reuse a QA, CI or personal identity. The owner's **master key stays offline**.
- **Escrow the mnemonic and the asset-lock transaction id** offline, in two places. Both are needed by `mint.mjs restore`, which re-creates the same identity from its original asset lock after a Platform reset ([forge-v2.md, Same-id restore](contracts/forge-v2.md#same-id-restore-after-a-platform-reset)). Record the identity id, the asset-lock `txid` and the creation height; pass the height as `--deployer-created-height`.
- **The deployer signs nothing but Forge registrations and updates.** Its identity-nonce sequence is part of the restore procedure. The script writes every transition it signs into `v2.nonceLedger` before it broadcasts. If something else signed with the deployer's identity (a key rotation, say), the next create stops until you name it with `--acknowledge-nonce <n> --note "<what it was>"`.
- **The CRITICAL key is present for the registration session only.** The script signs with the identity's CRITICAL authentication key and refuses a key that is missing, different from the file, or disabled on chain. Delete the file from the signing machine afterwards.
- **Testnet versus mainnet.** Testnet DASH is free from a faucet (see [Costs](guides/costs.md)). **Mainnet DASH is real money and there is no faucet:** fund the mainnet deployer through the bridge, and note that `tools/mint-identity` supports testnet and devnets only.

## 4. What it costs

Fees are credits (1 DASH = 10^11 credits) and are the same on every network of the same Platform release.

| Contract | Signed create | Cost |
|---|---|---|
| forge-core | 16,355 B | 0.5968 |
| forge-collab | 17,213 B | 0.3963 |
| forge-community | 15,425 B | 0.5063 |
| forge-meta | 6,890 B | 0.3636 |
| **The four** | | **about 1.86** |

Measured on devnet sakura, on Platform 5.0.0-beta.6, with the committed four-contract set (release-audit TEST-14, `testnet.md`). The three-contract devnet set cost about 1.73 (sakura's `costCredits` record). Fees did not change between beta.6 and the testnet's rc.3 release, and testnet's fee multiplier is 1 as on sakura, so expect the same on testnet; **to be re-measured on testnet** by the rehearsal, which prints each step's cost. Fund the deployer with about 2.5 DASH on testnet to leave room for a failed run and a restore (the restore replays the recorded costs plus 20 %).

On mainnet the same set costs the same number of DASH, in real money. A dry run costs nothing.

## 5. Register

```bash
# Once: the pinned SDK the script uses.
(cd forge-contracts/sdk-v2 && npm ci)

# Offline check of the id derivation.
node forge-contracts/scripts/deploy-v2.mjs --self-test

# The sums the owner signs.
node forge-contracts/scripts/deploy-v2.mjs --print-sha256 --set mainnet

# Dry run: build, validate and size all four transitions against the network. No sums needed.
node forge-contracts/scripts/deploy-v2.mjs --network <testnet|mainnet> --set mainnet \
     --identity <deployer.identity.json> --deployer-created-height <n> --dry-run

# Register core -> collab -> community -> meta in one new group.
node forge-contracts/scripts/deploy-v2.mjs --network <testnet|mainnet> --set mainnet \
     --identity <deployer.identity.json> --expect-sha256 <signed sums> \
     --deployer-created-height <n>
# -> writes forge-contracts/deployments/<network>.json (the `v2` record)
```

- Before broadcasting the script checks the protocol, rebuilds every contract with full validation locally, runs a preflight that builds and sizes every transition, and checks the refusals in [§2](#2-before-you-register).
- Each step's nonce, ids and pre-broadcast balance go into the record **before** it broadcasts. If a run is interrupted, **run the same command again**: it completes what landed and never registers a second copy. A run holds `<record>.lock` while it writes; one left by a killed run is deleted by hand after you have read the record.
- A node that reports a nonce below the last one the record shows signed is behind; the script asks again for a while, then stops without reserving anything.
- Do not pass `--force-new` unless you mean to supersede the live set: on testnet and mainnet it also needs `--abandon-live-set <network>`, because every client reads that set ([§8](#8-when-something-goes-wrong)).

Flags used on this page, all in `forge-contracts/scripts/deploy-v2.mjs`: `--set`, `--record`, `--scratch-on`, `--expect-sha256`, `--print-sha256`, `--deployer-created-height`, `--acknowledge-nonce` with `--note`, `--only`, `--update`, `--force-new` with `--same-group` or `--abandon-live-set`, `--replay` with `--replay-from-chain`, `--dry-run` and `--self-test`. Anything else in the script's header comment is documented there.

## 6. After registration

1. **Compare the chain with the signed JSON (C1).** Fetch all four contracts and compare each with the file whose sum was signed, ids substituted:

   ```bash
   node forge-contracts/scripts/freeze-c1-check.mjs --record forge-contracts/deployments/<network>.json \
        --contracts forge-contracts/contracts/mainnet --network <network> --report <c1.json>
   ```

   It checks config (writable, no moderation, `$formatVersion` 2), each `documentSchemas` and `schemaDefs` block key for key, the owner, version 1 and the recorded group. It is read-only and exits 1 on any mismatch. **Any mismatch stops the launch:** see [§8](#8-when-something-goes-wrong). Also check the group's owner and that it has no admins, and that all four are members.
2. **Freeze what was registered.** `node forge-contracts/scripts/freeze-registered.mjs --network <network>` checks each recorded source against its recorded hashes and writes the bytes registered to `forge-contracts/contracts/registered/<network>/<name>.v1.json`. It prints the `NETWORK_REGISTRATIONS` line `forge-contracts/schema/build.py` needs. From then on `validate-registered.sh` checks every later change as an additive update of those files.
3. **Snapshot the contracts for the web app.** `node forge-contracts/scripts/snapshot-contracts.mjs --network <network>` writes `forge-contracts/deployments/contracts/<network>.json`, which seeds the SDK's contract cache. Add `<network>` to the web app's contract-seed list; `lib/sdk/contract-seed.test.ts` fails while the snapshot and the record disagree.
4. **Wire the clients.** `forge-core` embeds every `deployments/*.json` at build time (`crates/forge-core/build.rs`), so committing the record is the whole Rust change. For `forge-web`, the network must be in `forge-web/lib/deployments.ts` (the `deployments bundle` unit test fails until it is) and the build uses `NEXT_PUBLIC_NETWORK=<network>`. See [BUILDING.md § Networks](BUILDING.md#networks).
5. **Check with `dg doctor --network <network>`.** The `contracts` check names forge-core, forge-collab, forge-community and forge-meta, the record as the source, and verifies they are enrolled in the group.
6. **Seed the labelled fixture and the showcase** with the QA identity, never a user's: `forge-contracts/deployments/fixtures/<network>.json` for the read tests, and `SHOWCASE` in `forge-web/lib/view/showcase.ts` for the landing page.

**Key exchange.** Mobile-wallet sign-in reads a key-exchange contract. Testnet uses yappr's, which the shipped wallets pin (recorded in `testnet.json` as `keyExchange`, "not deployed by Forge"). Mainnet's record names none; sign-in there needs one, and registering Forge's own copy is an owner decision (`deploy-key-exchange.mjs` refuses testnet and mainnet).

### What the registration PR commits

| File | What |
|---|---|
| `forge-contracts/deployments/<network>.json` | the `v2` record: the four contracts and their ids, the contract group with its owner, `chainId`, registration heights, per contract `sourceFile`, `sourceSha256`, `gitCommit`, `registeredSchemaHash`, `documentsHash`, `transitionSha256`, the deployer and `v2.nonceLedger`, `v2.contractsSet`, and DAPI seeds that run protocol 14 |
| `forge-contracts/contracts/registered/<network>/*.v1.json` | the bytes that were registered (`freeze-registered.mjs`), plus the `NETWORK_REGISTRATIONS` entry in `build.py` |
| `forge-contracts/deployments/contracts/<network>.json` | the contract snapshot (`snapshot-contracts.mjs`) |
| `forge-contracts/deployments/fixtures/<network>.json` | the read fixture, seeded by a labelled QA identity |
| the C1 output | the evidence that the chain equals the signed JSON |

Merging this PR changes what clients can reach. Rebuild and release every client afterwards: the ids are compiled in.

## 7. After registration: what can still change

Platform 5.0.0-rc.3 accepts an update to a contract only if it is additive. The owner can add **new document types** (with their own indexes) and **new optional properties**, as long as the contract stays under the transition size limit. Everything else is frozen:

| Frozen | Upstream |
|---|---|
| Contract config: `readonly` (an update that sets it, or touches a readonly contract, is refused), `keepsHistory`, `canBeDeleted`, the per-document defaults; moderation can be neither enabled nor dropped | `rs-dpp/src/data_contract/config/methods/validate_update/v0/mod.rs:17-131` (`v2` adds the moderation rule) |
| Each document type's config: `creationRestrictionMode`, `tradeMode`, `transferable`, `canBeDeleted`, `documentsKeepHistory`, `documentsMutable`, the encryption bounded keys, `signatureSecurityLevelRequirement`, count and sum flags | `rs-dpp/src/data_contract/document_type/methods/validate_update/common/mod.rs:111-401` |
| Index definitions (`validate_index_definitions_unchanged`), integer widths and encodings, action fees; `immutable` may only tighten | `rs-dpp/src/data_contract/document_type/methods/validate_update/v1/mod.rs:43-193` |
| Required fields: only a property the update adds may use `requiredSince` | `rs-dpp/src/data_contract/methods/validate_update/v1/mod.rs:91-115` |
| The contract's owner | `rs-dpp/src/data_contract/methods/validate_update/v0/mod.rs:110-133` |
| Schema keyword compatibility: a property may be added, an `enum` may gain values at the end, `required` may not grow | `rs-json-schema-compatibility-validator/src/rules/rule_set.rs` |

The first four rows are cited from the `v5.0.0-rc.3` audit; the required-fields row is from [forge-v2.md §9.1](contracts/forge-v2.md#91-update-1-and-the-mainnet-only-flags) (checked at beta.1). Line numbers drift between releases, so re-check them against the tag you register on; the paths are stable. [forge-v2.md §9](contracts/forge-v2.md#9-frozen-at-mainnet) lists what this means for Forge, type by type.

- **Check an update before you pay.** `tools/contract-validate <file> --expect-update contracts/registered/<network>/<name>.v1.json` fails when Platform would refuse the update. CI runs the same check on every pull request (`validate-registered.sh`, behind the `contract-validate` context).
- **Apply it.** `deploy-v2.mjs --update core|collab|community|meta|all` sends a `DataContractUpdate` (same id, same group, every document kept) and records it; rehearse it on the scratch set first.
- **A change the rules refuse** ships only as a new set (`--force-new`, [§8](#8-when-something-goes-wrong)). The documents under the old contracts stay under their ids and are no longer read.

## 8. When something goes wrong

Contracts cannot be rolled back, so the real window is **before the announcement**. Tag a release and announce only after C1 and the smoke tests pass.

| Situation | What to do |
|---|---|
| C1 does not match, or the smoke tests find a consensus defect, before anyone uses the network | Register a fresh set: `deploy-v2.mjs --network <network> --set mainnet --force-new --abandon-live-set <network> ...` (about 1.9 DASH; the guard exists because every client reads the live set). Regenerate the record, release a new client version and say which ids were abandoned. |
| A rule defect after launch that clients can enforce | A client-side refusal in `dg`, the push helper, the web app and the gateway, in a patch release, documented as a client rule. Additive fixes go through `--update` with the `--expect-update` gate. |
| A serious consensus hole after launch | Pause writes in the hosted app (the `PAGES_NOTICE` switch in [hosting](hosting.md)), re-register with `--force-new --abandon-live-set`, and release. Users re-push code, which lives in their own storage; collaboration data is lost unless it was exported. |
| **Platform reset that keeps Core** | Not a bad registration. Restore the deployer from its escrowed file (`mint.mjs restore`) and replay the record (`deploy-v2.mjs --replay --replay-from-chain <the record's chainId>`): the same ids come back and no client release is needed. [forge-v2.md](contracts/forge-v2.md#same-id-restore-after-a-platform-reset) has the steps and when it is impossible (a Core reset, a nonce gap over 24). |
| The deployer's CRITICAL key leaks | Replace the key from the offline master, audit the contract history, and publish an advisory naming any member added to the group; recommend `--strict-group` ([Contract group trust](contracts/forge-v2.md#contract-group-trust)). |
| The deployer's master key leaks | A client release that refuses the group, a new registration and a note telling users to rotate. |
| A client bug | A normal release: Pages redeploy or a new `dg` binary. No on-chain action. |
| External storage outage | `dg reseed --from-local` from any clone restores a lost copy at its recorded address. Refs and manifests on Platform are unaffected. |

## 9. Hosting and smoke tests

- **The web app.** The static export deploys to GitHub Pages (`.github/workflows/pages.yml`, from `master`) with `NEXT_PUBLIC_NETWORK` from the repository variables `PAGES_NETWORK` and `PAGES_DEVNET_NAME`. Set the variables, and the gateway URL, only when the gateway for that network is ready, because the build bakes the gateway URL into clone rows and share links. Optionally publish the release's IPFS build ([Verify the app you loaded](guides/verify-the-app.md)).
- **Smoke tests.** After registration, run the CLI smoke suite (`e2e/cli/run.sh`) and the web Playwright suite against the network with a labelled QA identity. Registered repositories, issues and Platform-stored packs cannot be deleted, so reuse one smoke repository with a fresh branch per run.
- **Dogfood.** Host the Forge repository itself on the network once it is live and keep the GitHub copy and the [Mirror Action](guides/mirror-a-github-repo.md) running.
